# 教师作业 AI/人工批改闭环任务

## 最终目标

实现正式作业业务闭环，而不是继续扩展评测工作台：

教师创建作业、题目、参考答案和结构化评分标准并发布 → 学生按题目提交文本或附件 → 截止时间到达后教师一键启动 AI 批改或逐题人工批改 → 系统按题目形成评分记录并按学生聚合 → 教师逐份查看、修改、确认 → 教师逐份发布结果 → 学生看到最终分数、教师确认后的批注、参考答案和评分标准。

本变更优先验证业务闭环、权限、状态机、幂等性和可见性；当前 Qwen 评分质量不作为闭环实现的阻塞条件。

## 交付边界

### 必须实现

- 复用现有 `Assignment`、`AssignmentRevision`、`AssignmentQuestion`、`AssignmentSubmission`、`SubmissionAnswer`、`GradingRun` 和教师审核链路。
- 所有作业同时支持 AI 批改和人工批改，不增加作业级 AI 启用开关。
- 仅在作业截止后允许批改；学生上传不触发自动批改，截止时间也不自动触发批改。
- AI 批改按题目执行，单题失败不阻塞同一学生其他题目。
- 人工评分建立明确来源为 `MANUAL` 的评分记录，不伪造 Provider 调用。
- 教师确认单位是学生整份作业，发布单位也是学生整份作业；不支持单题学生端发布。
- 发布包绑定最终分数、教师确认后的批注、参考答案和评分标准，四者不可分离发布。
- 新发布作业禁止按时间自动揭示参考答案；历史作业保留既有 `AT_TIME` 行为。
- 补交生成新提交版本，进入后续增量批改；原提交、原批次、原结果和退回原因保留。
- 继续使用现有脱敏门禁；Provider 不接收姓名、学号、班级身份、本地路径或未确认脱敏的数据。

### 不在本变更内

- 不调整 Qwen 模型评分方式、提示词质量或当前评测门槛。
- 不上传答题记录；答题记录只作为本地人工分数对比依据，不进入 Provider、ZIP 或 Git。
- 不新建平行作业、提交、评分或 AI Provider 系统。
- 不把 AI 完成等同于教师确认，不自动向学生发布 AI 原始结果。
- 不强制整班同时发布；某个学生确认完成即可独立发布。
- 所有教师与学生 UI 变更必须在现有作业区域内扩展，复用既有布局、组件、状态表达和交互模式，保持与原界面相似的视觉风格。

## 阶段任务

## 阶段 0：基线、契约与迁移设计

- [x] 0.1 读取现有作业发布、学生提交、教师审核、评分运行和学生作业页面，绘制当前状态与目标状态的差异清单。
- [x] 0.2 确认 `AssignmentRevision` 发布快照包含题干、参考答案、结构化评分标准、题目顺序和满分，并定义新作业的结果发布策略标识。
- [x] 0.3 设计评分来源、批改批次、学生作业聚合、题目失败/重试、教师确认和学生发布包的数据契约。
- [x] 0.4 设计历史作业兼容规则：历史 `AT_TIME` 不迁移，新发布作业只能使用教师确认发布规则。
- [x] 0.5 为状态转换、教师权限、学生可见性、幂等键和并发写入建立错误码与审计字段清单。
- [x] 0.6 完成 OpenSpec proposal/design/spec delta，并通过 `openspec validate <change> --type change --strict`。

## 阶段 1：教师发布与冻结评分输入

- [x] 1.1 发布前强制校验每道题具有题干、参考答案和结构化评分标准；不完整时拒绝发布。
- [x] 1.2 发布时冻结题目、答案、量规、题目顺序、满分和发布策略，批改过程只读取冻结快照。
- [x] 1.3 新发布作业拒绝 `AT_TIME` 答案揭示配置，并返回教师可理解的校验错误。
- [x] 1.4 保持历史作业的 `AT_TIME` 读取和揭示行为，不改变既有历史数据语义。
- [x] 1.5 为每个学生提交冻结其所属 audience 与原截止时间；同一 revision 的不同 audience 按各自截止时间判定批改资格。
- [x] 1.6 在教师发布界面明确显示：截止后可选择 AI 或人工批改，答案和评分标准须随确认结果发布。
- [x] 1.7 增加发布契约、快照不可变性、历史兼容和越权测试。

## 阶段 2：学生按题目提交与截止控制

- [x] 2.1 复用现有按题目文本/附件提交接口，不新增整份 Word 上传协议。
- [x] 2.2 验证学生只能提交到已发布且对其开放的作业 revision，并保持现有提交幂等性和版本链。
- [x] 2.3 明确截止前提交、截止后拒绝、教师授权补交和新提交版本的状态转换。
- [x] 2.4 补交只能在原作业截止时间到达后，由教师退回并授权；截止前不提供补交路径。
- [x] 2.5 已提交但缺题的学生保留缺题状态；缺题不得自动计零，后续由教师明确确认未作答或不计分。
- [x] 2.6 从未提交整份作业的学生不进入 AI 批改范围。
- [x] 2.7 增加截止边界、附件权限、重复提交、缺题和补交授权测试。

## 阶段 3：截止后批改执行

- [x] 3.1 为评分记录增加明确来源区分：`AI` 与 `MANUAL`；人工记录必须有教师操作者和修改时间，不产生 Provider 调用。
- [x] 3.2 新增教师一键 AI 批改入口：截止后可用，默认选择所有已提交且待批改学生，支持启动前排除学生。
- [x] 3.3 以不可变整份提交快照、冻结 audience 和按题目 attempt 向量创建可审计批改批次，保证重复点击只返回幂等结果，不重复覆盖历史运行。
- [x] 3.4 按题目创建评分执行；单题失败只标记该题失败，其他题目继续执行。
- [x] 3.5 支持失败题目显式重试 AI；重试仍失败时允许转人工，保留所有尝试、失败原因和历史结果。
- [x] 3.6 提供教师逐题人工批改入口，支持完全人工批改、AI 后人工修改和 AI 失败转人工。
- [x] 3.7 外部 Provider 调用前执行脱敏确认和最小数据投影；失败时 fail-closed，不发送原始身份或本地路径。
- [x] 3.8 题目级反馈 outbox 对新确认发布作业只准备派生产物，不得在整份结果确认/发布前使学生可见。
- [x] 3.9 增加截止前拒绝、按 audience 截止、批次幂等、并发启动、来源记录、失败隔离、重试和 Provider 脱敏测试。

## 阶段 4：作业级聚合、审核与确认

- [x] 4.1 按不可变整份提交快照聚合各题状态、分数、批注、来源和失败信息，题目执行仍保持独立。
- [x] 4.2 定义完整性门禁：每道题必须有 AI 评分、人工评分或教师明确结论；缺题和失败不能静默通过。
- [x] 4.3 教师可在整份作业视图逐题查看 AI 原始结果、人工结果、来源、失败原因和修改历史。
- [x] 4.4 教师可逐题修改分数与批注；人工修改成为当前优先结果，后续 AI 批次不得覆盖已确认结果。
- [x] 4.5 只有整份作业满足完整性门禁后，教师才能执行该学生作业的确认操作。
- [x] 4.6 确认操作记录操作者、确认时间、结果版本、attempt-vector hash 和所用冻结答案/量规版本，并保持幂等。
- [x] 4.7 增加部分题目失败、缺题、人工覆盖、版本冲突、越权确认和并发确认测试。

## 阶段 5：逐份发布与学生可见结果

- [x] 5.1 新增教师逐份发布入口；已确认学生可发布，不受其他学生失败、未批改或待处理状态阻塞。
- [x] 5.2 发布时一次性绑定最终分数、教师确认后的批注、参考答案和评分标准，禁止分别发布。
- [x] 5.3 新发布作业的题目级反馈派生产物只能被作业级发布包引用；学生接口不得直接消费题目级 feedback release。
- [x] 5.4 学生端只向已发布该学生结果的用户返回发布包；未确认/未发布时隐藏分数、批注、参考答案和评分标准。
- [x] 5.5 学生端正确展示按题目分数、总分、教师确认后的批注、参考答案和评分标准；AI 原始记录和教师修改历史不可见。
- [x] 5.6 新发布作业不再走按时间揭示答案路径；历史作业继续按旧策略兼容读取。
- [x] 5.7 增加学生越权读取、答案提前泄露、分离发布、逐份发布和历史 `AT_TIME` 兼容测试。

## 阶段 6：补交与增量批改

- [x] 6.1 仅在原作业截止后复用教师退回机制授予补交权限并设置新的截止时间，不提供学生自助绕过授权的补交路径。
- [x] 6.2 补交创建新的提交版本，原提交、原批次、原评分、原确认/发布状态和退回原因全部保留。
- [x] 6.3 补交版本进入新的待批改集合，不自动加入正在运行或已完成的旧批次。
- [x] 6.4 再次一键批改只处理新增且尚未批改的版本；已确认结果不被自动重跑覆盖。
- [x] 6.5 补交结果重新经过题目评分、整份聚合、教师确认和逐份发布门禁。
- [x] 6.6 增加补交授权、版本隔离、旧结果保留、增量批次和并发重跑测试。

## 阶段 7：教师/学生界面、集成验收与交付

- [x] 7.1 在现有教师作业区域增加截止后批改控制台：待批改学生、批次状态、一键 AI 批改、排除学生、重试和人工批改入口；复用现有教师作业页面的布局、组件与视觉风格。
- [x] 7.2 增加学生整份作业审核页：逐题结果、来源、失败/缺题状态、修改、确认和发布操作；保持与现有教师审核界面一致的交互和状态表达。
- [x] 7.3 在现有学生作业页接入提交状态和已发布结果包，不泄露教师内部评分信息，并保持原学生作业页面的视觉风格和响应式行为。
- [x] 7.4 为关键状态显示明确文案：未到截止、待批改、批改中、部分失败、待教师确认、已发布、补交待批改。
- [x] 7.5 完成 Route Handler、服务层、数据库集成、浏览器交互和可见性回归测试。
- [x] 7.6 运行定向测试、受影响 ESLint、typecheck、OpenSpec strict validate、`git diff --check`；记录未解决的模型质量风险但不把其伪装成闭环通过。
- [x] 7.7 完成教师和学生最小端到端验收：发布一份作业、两名学生提交、截止后分别 AI/人工批改、教师修改并确认、逐份发布、学生读取结果、补交后增量批改。

## 阶段完成门槛

- 每个阶段的全部任务完成后，必须立即更新本文件的勾选状态和 `HANDOFF.md` 中的实现事实、验证证据、残余风险及下一阶段前置条件。
- 文档维护完成后，必须启动一个与实现工作独立的只读 `Sol high` 子代理审核该阶段的实际 diff、OpenSpec 契约和验证证据；审核代理不得编辑代码或文档。
- 只有审核明确通过，或所有被接受的阻塞问题已在本阶段完成一次修复和限定复审后，才能将下一阶段置为进行中。
- 审核发现必须由主线程判定为 `ACCEPT`、`REJECT` 或 `DEFER`；`ACCEPT` 的阻塞问题未解决前不得进入下一阶段。
- 审核无阻塞问题时，`HANDOFF.md` 必须记录审核范围、结论、审核模型与验证依据；不以口头结论代替审计记录。
- 阶段 1 完成后，新发布作业的评分输入和答案揭示策略不可绕过。
- 阶段 3 完成后，截止后 AI、人工、失败隔离和批次幂等链路可运行。
- 阶段 5 完成后，教师确认后逐份发布和学生结果读取闭环可运行。
- 阶段 6 完成后，补交不会覆盖历史结果，并能独立进入增量批改。
- 阶段 7 完成后，业务闭环通过集成验收；评分质量问题单独记录，不阻塞本次闭环交付。

## 交付后的已知风险

- 当前 Qwen 对部分题型的评分一致性不足，尤其是图文证据和量规边界；本变更只保证流程正确，不宣称模型质量达标。
- 逐份发布后，学生可能在平台外转发参考答案和评分标准；平台只保证未发布学生在平台内不可访问。
- 历史 `AT_TIME` 作业与新确认发布作业并存，接口和学生端必须依据 revision 的发布策略分支处理。
