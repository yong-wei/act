# 独立验证 FFT 海洋与 WebGPU/TSL 的投入产出 — 设计

基线：`37a988f5928d73c2af7eabad57284a771c9d3519`。共同依据与上游来源：[研究报告](../../../docs/research/2026-09-17-marine-environment.md)。所有性能/误差数值为待验证目标。

## 技术先决条件

使用已稳定的水体光学与真实性能观测：`implement-marine-water-optics`、`govern-marine-render-performance`。本项不阻断全舰生产迁移。

## 实验设计

保持几何可见密度、材质/环境、镜头、船包、drawing buffer 和泡沫选项尽量相同；先比较波场算法，再比较后端，不能让 WebGPU 方案同时换天空/材质而把全部收益归给 FFT。

候选从小分辨率和有限频率级联开始，例如 128²/256²、一至两个级联，仅为实验起点；每个级联覆盖不同频带，避免重复计算能量。记录方向谱、峰值周期、有效波高的定义和空间/时间统计，不能仅看一张截图。

WebGL 可用 render-target ping-pong/GPGPU；WebGPU 可用计算管线，但 ACT ShaderMaterial/onBeforeCompile 和现有 post 不保证直接兼容。明确浏览器/版本特性门槛和失败行为，不把 Three 后端回退等同于自定义 FFT compute 自动回退。

高频波场只在 GPU 时，需证明少量船体查询方案不会逐帧同步读回整张纹理，且满足当前可见曲面/接触误差。可以评估低频解析表示加谱光学细节，但要明确统计/几何与姿态间的近似责任，不另建一份不一致波场。

评估 Poseidon、旧 WebGL FFT、Takram/Bruneton 大气仅作为一手实现参考，核查许可、维护、依赖和可迁移代码边界；不因为 README 功能多就直接纳入生产依赖。不为本项搭建完整 GIS 或流体引擎。

## 决策输出

保存可复现实验、参数、测量和视觉证据；结论可以是保留当前路线。只有在明确视觉收益、目标硬件预算、接口一致性和维护成本均可接受时，才提出下一项单独迁移 change；本项不修改生产 renderer 或默认质量。
