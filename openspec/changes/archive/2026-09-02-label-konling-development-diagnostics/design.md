## Context

`buildStreamingCitationFallbackNotice` 已根据 `NODE_ENV` 和显式 override 决定是否生成详细诊断。开发分支会把来源、缺失引用类别、缺失上下文、低置信原因和个性化状态拼入同一文本块，但文本没有开发诊断标记；生产安全提示又使用相同的“控灵证据提示”前缀，造成两种语义混淆。

## Goals / Non-Goals

**Goals:**

- 让任何允许进入浏览器的完整诊断都带有明确且稳定的开发/支持诊断身份。
- 让诊断文本与正式引用元数据和学生学习内容可区分。
- 保持生产默认不出现 raw reason code。

**Non-Goals:**

- 不取消 #693 允许的开发诊断注入。
- 不改变引用守卫的判定、检索、持久化或模型提示词。
- 不把内部诊断字段改造成新的学生学习事实。

## Decisions

### 1. 标识跟随可见诊断，而不是跟随环境字符串

是否允许注入由现有环境/override 策略决定；一旦允许详细诊断进入流，前缀必须明确写出开发模式或支持诊断。生产默认的安全限制提示继续使用产品语言，不携带内部 token。

### 2. 诊断和正式引用保持两个语义区块

诊断前缀、内部 reason code 和最终 CitationPanel 不共享“已验证引用”的视觉或语义标记。最终引用继续从服务端元数据渲染。

### 3. 用文本契约锁定边界

单测覆盖完整开发诊断、生产默认隐藏和显式 override；测试断言既包含诊断标识，也保留生产 raw token 不可见约束。

## Risks / Trade-offs

- 可见开发诊断会继续暴露内部字段给具备开发环境访问权的人，这是 #693 明确保留的排障能力；本变更只修正身份标识，不扩大其范围。
- 支持调试 override 的使用者可能不是开发者，因此标识使用“开发/支持诊断”类产品语言而不是把它伪装成学生反馈。

## Migration Plan

更新诊断文本构造和单测；无需数据迁移，既有持久化 metadata 不变。

## Open Questions

None. 现行 spec 已规定开发模式诊断必须可识别。
