# Design: Run-specific QA evidence lifecycle

## Baseline and characterization

The baseline is `edb98945e78ab0824f801806751fd57f97056347`. The denominator is
5,528 tracked files under `artifacts/`, with 1,364 commercial UI files and
2,860 product-design audit files, plus all source imports and path references
to run-specific evidence. Characterize the five review clients, simulation
shell/page, control-workbench shell, `commercial-ui-capture-revision`, and
`commercial-ui-governance` before editing. For each reference record whether it
is a deterministic fixture, a receipt/manifest, a run output, or a closure
document, its caller, source revision, privacy class, and retention decision.

## Artifact classes

1. **Representative fixtures:** small deterministic inputs or screenshots that
   are intentionally source-controlled for stable route/component tests. They
   contain no credentials, cookies, user identifiers, raw answers, or local
   absolute paths.
2. **Run receipts and manifests:** source-controlled or published small records
   containing route, theme, viewport, role, browser/tool version, source/tree
   revision, capture revision, output hash/reference, privacy class, and status.
   They are not themselves proof that a missing external output exists.
3. **Run outputs:** screenshots, traces, HARs, logs, and temporary staging files
   generated by a local/CI/nightly run. They live in CI artifact storage or
   approved object storage, addressed by hash and retention policy.
4. **Audit/closure documents:** product-design or governance records retained
   under their canonical ledger, with links to a portable manifest rather than
   embedding an application import path.

## Product boundary

The production/web graph may import deterministic fixtures and typed manifest
metadata through a bounded evidence package. It may not import a run directory,
timestamped screenshot, trace, HAR, log, or local `artifacts/` path. Review
pages that need visual material resolve a representative fixture or a validated
published package by manifest identity. Runtime simulation/control-workbench
code keeps product behavior independent from QA evidence.

## Commercial capture integration

The capture runner continues to use the active contract from
`stabilize-commercial-ui-qa-capture-contract`: explicit service URL, development
revision probe, Dock readiness, temporary staging, and transactional publication
to the final evidence root. The existing route/theme/viewport/role matrix and
product evidence checks do not change. After capture, the tool emits a portable
manifest and external references; missing, stale, hash-mismatched, or privacy-
unsafe output fails the governance gate.

## Migration and external storage

Inventory and classify all artifact references, replace product imports with
fixtures or manifest resolution, and publish large outputs to CI/object
storage. Verify hashes and source/capture identity before accepting a receipt.
Delete only tracked run outputs whose references have migrated and whose
retention decision is recorded; keep canonical representative evidence and
audit-ledger documents. The deletion receipt lists exact paths, hashes, reason,
and recovery/retention status. No broad or unclassified deletion is allowed.

## Verification, privacy, and non-goals

Run import-boundary checks, deterministic fixture tests, manifest/hash checks,
commercial UI governance tests, portable-path/privacy scans, and a representative
CI artifact fetch. Credentials and user/private evidence are rejected before
publication. This design does not change selectors, runtime semantics,
deployment, or production activation.
