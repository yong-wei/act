## Context

The 4-7 live classroom session showed that the interactive data-governance pipeline is operational but not yet evidence-complete. The session produced a ready class report, 375 LearningFacts, a class snapshot, and student snapshots. However, objective quiz answers were not preserved in immutable `StudentStepResponse.responseData`; the answer details had to be recovered from mutable `StudentState.data.responses`. `LearningFact.score` stayed at zero, so correctness did not feed the evidence layer. `sync_error` events also appeared in bursts from only two accounts, producing 891 error logs and making interaction totals harder to interpret.

The implementation must preserve existing classroom runtime behavior while making the post-class governance records trustworthy enough for analytics, reports, and later review.

## Goals / Non-Goals

**Goals:**

- Make `StudentStepResponse` the durable source for submitted quiz answers, not just a metadata shell.
- Make objective quiz LearningFacts carry score and correctness context derived from the submitted answer payload.
- Keep `ClassSessionReport` counts reproducible from stored `InteractionLog`, `StudentStepResponse`, `LearningFact`, and snapshot records.
- Add sync-error burst handling so localized retry loops are visible as incidents without inflating class-wide activity.
- Add tests that reproduce the 4-7 evidence pattern: many participants, two quiz steps, repeated attempts, snapshot updates, and a concentrated sync-error burst.

**Non-Goals:**

- Rewriting 4-7 course content, prompts, or correct answers.
- Replacing the data-governance worker architecture.
- Changing the lesson runtime event API unless current payloads cannot carry the required answer data.
- Recomputing all historical sessions by default. Historical backfill may be a separate optional script.

## Decisions

1. Preserve answers at ingestion time.

   Interactive submit events should store the submitted answer object in `StudentStepResponse.responseData`, including `stepId`, `lessonKey`, `attemptKey`, card ids, selected values, and per-card correctness when available. This keeps the immutable submission table aligned with what the student submitted even if `StudentState` is later overwritten.

   Alternative considered: continue deriving answers from `StudentState`. That is insufficient because `StudentState` is current-state storage and loses evidence semantics such as all attempts and exact submitted payloads.

2. Score LearningFacts from quiz-card contracts.

   For objective quiz cards with known `reference_answer`, `rubric`, or manifest options, the ingestion path should compute a per-card correctness map and an aggregate score. `LearningFact.contextJson` should preserve the scoring basis, while `LearningFact.score` should represent the normalized score for that fact or attempt.

   Alternative considered: leave score calculation to report-time analysis. That would keep reports dependent on lesson-specific reconstruction and would not improve profile and snapshot evidence.

3. Treat sync-error bursts as telemetry incidents, not normal activity.

   Sync errors should remain observable, but report summaries should group repeated identical errors by user, step, and short time window. The report should expose both raw error count and deduplicated incident count so debugging detail is not lost.

   Alternative considered: drop sync errors entirely. That would hide real classroom synchronization failures and make production diagnosis worse.

4. Make report counts auditable.

   `ClassSessionReport.reportData` should name the source and calculation policy for participants, logs, submissions, facts, sync errors, and snapshot coverage. The report should avoid mixing raw logs and deduplicated incidents without labels.

5. Keep schema changes optional.

   Existing JSON columns appear sufficient for the required payloads. The default implementation should avoid a Prisma migration unless tests prove that queryability or record size requires new columns.

## Implementation Field Mapping

- `lessonKey`: taken from the interactive event top-level `lessonKey`, copied into `InteractionLog.lessonKey`, `StudentStepResponse.lessonKey`, `LearningFact.lessonId`, and `contextJson.interactiveQuiz.lessonKey`.
- `stepId`: taken from the event top-level `stepId` or payload `stepId`, copied into `InteractionLog.stepId`, `StudentStepResponse.stepId`, `LearningFact.moduleId`, and `contextJson.interactiveQuiz.stepId`.
- `clientEventId`: resolved from event `id` or payload `clientEventId`; used for event de-duplication, source-log attachment, `StudentStepResponse.clientEventId`, and scoring context.
- `attemptKey`: generated by the student page as `<stepId>:response:<submittedAt>` and copied to `InteractionLog.attemptKey`, `StudentStepResponse.attemptKey`, and scoring context.
- `sourceLogId`: never trusted from the client; attached after `InteractionLog.createManyAndReturn()` and copied to `StudentStepResponse.sourceLogId`, `LearningFact.sourceLogId`, and scoring context.
- `card id`: taken from manifest activity card ids and emitted as `questionSummaries[].questionId`, then preserved in `StudentStepResponse.responseData` and `LearningFact.contextJson.interactiveQuiz.cards[]`.
- `selected value`: taken from manifest step response `answers[card.id]`, emitted as `questionSummaries[].studentAnswer`, and preserved in durable response data and scoring context.
- `reference answer`: taken from manifest activity card `referenceAnswer` for objective cards; used to compute per-card correctness and normalized quiz score.

## Risks / Trade-offs

- Existing historical sessions may still have metadata-only `StudentStepResponse` records. Mitigation: provide a one-off local backfill or analysis command only if required; do not silently mutate production history during the main fix.
- Scoring from manifest contracts can be brittle if a lesson stores answer keys inconsistently. Mitigation: implement a narrow objective-quiz scoring adapter with explicit unsupported states and tests for missing answer keys.
- Deduplicating sync errors may hide severity if only the deduplicated count is shown. Mitigation: reports must keep both raw and deduplicated counts.
- Repeated submissions can either represent retry behavior or repeated clicks. Mitigation: preserve all attempts in `StudentStepResponse`, and calculate final-state summaries separately from attempt summaries.
