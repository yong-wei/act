# Codex 子代理 Harness 契约

本文定义本项目在 Codex 中使用 custom agents 的主线程 harness。它不是插件系统，不需要运行时编排器；它是给主线程和子代理共同遵守的文档契约。

## 核心原则

1. 主线程是唯一调度者和最终裁决者。
2. `agent-router` 只提出调度建议，不直接派发代理，也不替代主线程判断。
3. 子代理深度固定为 1。
4. 读代理可并行，写代理串行。
5. 每次派发必须有 brief，每次汇总必须有取舍。
6. 子代理输出是证据，不是结论本身。

## 标准 6 步流程

### 1. 授权判断

用户明确授权当前任务、会话、分支或 review 使用子代理后，才进入多代理流程。没有授权时，主线程保持单代理执行。

### 2. 路由判断

主线程先判断是否需要 `agent-router`。当任务跨多个领域、风险不清、可能需要 3 个以上子代理或用户明确要求“选择子代理”时，先调用 `agent-router`。否则直接选择最小代理集。

### 3. Brief 编写

每个子代理 brief 至少包含：

```md
目标：
范围内：
范围外：
已知文件/模块：
允许权限：read-only / workspace-write
禁止事项：
输出格式：
验证命令或停止条件：
父线程已知假设：
```

### 4. 只读并行

可并行调用 `code-mapper`、`explorer-librarian`、`spec-planner`、各类 reviewer。只读代理不得编辑文件，不得把证据总结包装成最终裁决。

### 5. 写入串行

`spark-coder`、`patch-worker`、`test-engineer` 属于写代理。不得并行修改同一工作树。写代理完成后必须报告修改文件和验证结果。

### 6. 主线程汇总与复核

主线程必须说明：

- 哪些子代理意见被采纳。
- 哪些意见被拒绝及理由。
- 哪些风险已验证。
- 哪些假设仍未验证。
- 是否需要继续调用 `critical-reviewer` 或领域 reviewer。

## 任务风险等级

| 风险等级 | 典型任务 | 默认代理规模 |
| --- | --- | --- |
| low | 单文件文案、局部配置、小样板 | 0-1 |
| medium | 有明确路径的功能、小 bug、小 UI 行为 | 1-3 |
| high | 跨模块改动、数据治理、AI 上下文、仿真/Arena、Prisma | 2-4 |
| release-critical | 发布、迁移、完整分支/PR、生产风险 | 4-6 |

## 写代理串行规则

- `spark-coder`：只能做小补丁，越界立即停下。
- `patch-worker`：做生产代码最小安全实现。
- `test-engineer`：做测试与验证；可写测试，但不应修生产逻辑。
- `deep-debugger`：虽然具备 workspace-write，但只用于诊断命令、临时产物或父任务明确授权的诊断性改动；正式修复交给 `patch-worker`。

## 冲突处理

当子代理意见冲突时，主线程按以下优先级处理：

1. 明确复现、测试或代码路径证据优先于抽象判断。
2. 领域 reviewer 对本领域语义具有更高权重，例如控制理论交给 `simulation-domain-reviewer`，学习画像交给 `data-governance-reviewer`。
3. `critical-reviewer` 负责终审风险排序，但不能覆盖领域事实。
4. 主线程必须写明取舍理由。

## 停止条件

出现以下情况应停止继续 fan-out：

- 已经有明确最小修复路径。
- 继续增加代理只会重复已有证据。
- 子代理输出冲突但缺少新证据来源。
- 当前任务没有用户授权使用更多子代理。
- 写代理已经修改工作树，后续需要先验证或 review，而不是继续并行写入。
