可以实现，而且**不建议只靠“为每个页面手工预置整段上下文，然后唤起时整段注入”**。
更稳妥的做法是把它设计成一个**分层上下文注入系统**：固定层不变，页面层动态生成，用户层按需补充。这样更可扩展，也更省 token。

我先给结论：

**最推荐的方案**是“**页面元数据 + 页面内容抽取 + 路由感知 + 运行时上下文组装**”的混合架构。
也就是：

1. 系统层：固定注入智能体身份、风格、边界。
2. 用户层：固定注入用户画像、课程角色、历史偏好。
3. 页面层：根据当前路由与页面状态，动态生成当前页上下文。
4. 知识层：必要时再检索课程知识库、教学目标库、知识图谱，而不是每次都塞进 prompt。

这本质上属于运行时外部上下文注入，和 RAG 的思路一致：不是把所有知识预烘焙到提示词里，而是在请求时动态取最相关内容注入。OpenAI 对 RAG 的定义也是“在运行时把外部上下文注入 prompt 以提升回答相关性”。([OpenAI Help Center][1])

## 一、你要解决的其实是三个问题

### 1. 助手怎么知道“现在在哪个页面”

这属于**页面定位 / 路由感知**问题。

对于传统多页应用，可直接读 URL。
对于 React / Vue / Next.js 这类 SPA，页面切换常通过 History API 的 `pushState` / `replaceState` 完成，并在回退时触发 `popstate`，因此可以通过路由监听来感知页面变化。([MDN Web Docs][2])

### 2. 助手怎么知道“这个页面此刻的核心内容是什么”

这属于**页面语义抽取**问题。

如果页面内容会动态刷新，单靠初始 HTML 不够，需要在前端监听组件更新或状态更新。浏览器原生可用 `MutationObserver` 监听 DOM 树变化。该 API 专门用于观察 DOM 变化，且已是较成熟的标准能力。([MDN Web Docs][3])

### 3. 助手怎么把这些信息以可控方式注入模型

这属于**上下文编排**问题。

不应该把整页 DOM 或所有教学材料无脑塞进去，而应做成结构化上下文对象，然后按优先级注入：
“页面类型 → 当前教学任务 → 当前知识点 → 当前活动 → 页面关键数据 → 用户画像 → 系统提示词”。

## 二、可选技术方案

下面按复杂度和效果，从低到高分析。

---

## 方案 A：每个页面手工预设静态上下文映射

### 做法

为每个页面维护一份配置表，例如：

```json
{
  "/course/auto-control/chapter/3": {
    "page_type": "知识学习页",
    "teaching_goal": "理解时域指标及其物理意义",
    "assistant_focus": "优先解释调节时间、超调量、峰值时间之间关系",
    "allowed_actions": ["答疑", "举例", "生成练习题"]
  }
}
```

用户在该页面唤起助手时，前端把：

* 固定系统 prompt
* 用户画像
* 当前页面配置

一起发给后端组装 prompt。

### 优点

* 实现最简单
* 结果可控
* 很适合页面数量不多、结构稳定的平台

### 缺点

* 维护成本高
* 页面一多就爆炸
* 页面中如果有动态内容，这套方案感知不到
* 只能知道“页面是什么”，不知道“页面当前展示了什么”

### 适用场景

* 平台刚起步
* 页面类型有限
* 先验证产品可行性

### 评价

这是最容易落地的 MVP，但不建议作为最终方案。

---

## 方案 B：路由级静态配置 + 页面状态动态补充

### 做法

仍然保留每个页面或页面模板的“教学意图配置”，但不是只注入静态文本，而是再加一层**运行时数据抽取**。

例如一个“根轨迹分析页”可能有固定配置：

```json
{
  "page_type": "仿真实验页",
  "teaching_goal": "理解开环增益对闭环极点分布的影响",
  "assistant_focus": "引导学生观察极点移动与系统性能变化"
}
```

但页面运行时再补充：

```json
{
  "current_k": 3.2,
  "observed_overshoot": "较大",
  "selected_module": "根轨迹交互实验",
  "student_action": "已尝试两次参数调节"
}
```

最后注入模型的是一个结构化包，而不是一整段死文本。

### 优点

* 控制力和动态性平衡较好
* 可以覆盖绝大多数教学页面
* 易于工程化

### 缺点

* 前端页面需要暴露“上下文提取接口”
* 需要统一不同页面的数据结构

### 适用场景

* 你的 ai-obe 平台这种教学平台
* 页面类型多，但仍可归类
* 希望助手真正“看懂当前页在做什么”

### 评价

这是我认为**最适合你当前平台阶段**的方案。

---

## 方案 C：纯页面内容自动抽取，不做手工配置

### 做法

不为每页手工建上下文，只在助手被唤起时，自动读取当前页面：

* 标题
* 面包屑
* 课程名
* 小节名
* 页面正文主内容
* 表单/表格/图表摘要
* 当前按钮状态
* 学生操作记录

然后用一个小型 summarizer 或规则引擎，把这些内容压缩成“当前页语义摘要”，再注入主模型。

### 优点

* 自动化程度高
* 页面新增后无需手工维护
* 更接近通用 Copilot

### 缺点

* 容易抽到噪声
* 对 DOM 结构依赖大
* 对复杂页面、图表页、虚拟仿真页不稳定
* 很难准确提取“教学目的”，因为教学目的常常不在页面显式文本里

### 适用场景

* 文档页、说明页、知识点页
* 页面结构规范统一

### 评价

单独使用风险较大。
因为“教学目的”往往是平台设计者定义的，不一定能从页面文本自动推断出来。

---

## 方案 D：知识图谱 / 页面语义注册表驱动的动态上下文

### 做法

把页面不只是看作 URL，而是看作一个“教学节点”。
例如每个页面在后台注册如下元数据：

* 页面 ID
* 所属课程
* 所属章节
* 关联知识点
* 前置知识
* 后继知识
* 对应课程目标
* 对应毕业要求指标点
* 页面任务类型（讲解 / 练习 / 实验 / 讨论 / 测验）
* 教学目标
* 常见误区
* 推荐引导方式

当用户进入页面时，系统根据 page_id 查询“页面语义注册表”，再结合当前页面实时状态生成上下文。

### 优点

* 语义非常清楚
* 特别适合 OBE、课程目标映射、知识图谱平台
* 有利于后续做诊断、推荐、学情分析
* 能把“教学意图”做成一等公民，而非附属备注

### 缺点

* 前期建模成本高
* 需要统一页面与知识点映射机制
* 需要后台数据库支持

### 适用场景

* 你这种 ai-obe 平台，非常适合
* 后续希望做个性化推荐、形成性评价、知识追踪

### 评价

这是**中长期最优架构**。

---

## 方案 E：运行时检索式上下文注入（RAG）

### 做法

不把所有页面上下文提前存死，而是当助手被唤起时，根据当前页面的以下信息发起检索：

* page_id
* course_id
* chapter_id
* activity_type
* user_role
* 当前操作状态
* 当前提问内容

然后从知识库中检索最相关的：

* 页面说明
* 教学目标
* 知识点解释
* 常见错误
* 例题
* 学生画像适配策略

再拼成 prompt。

### 优点

* 上下文更精确
* token 更省
* 容易扩展
* 适合大规模课程内容

### 缺点

* 检索质量决定回答质量
* 工程链路更复杂
* 对结构化数据和向量索引有要求

### 适用场景

* 内容量大
* 希望多个课程共用一个助手底座
* 希望长期扩展成平台级智能体

### 评价

如果平台未来会扩展到很多课程、很多教学活动，这个方案很值得做。
RAG 的基本思想就是在运行时检索并注入外部上下文，而不是静态塞满提示词。([OpenAI Help Center][1])

---

## 三、最关键的问题：是否需要提前为每个页面建立上下文？

答案是：

### 不是必须“每页一段完整 prompt”

但**最好提前为“页面类型”或“教学节点”建立结构化元数据**。

也就是说，不建议这样做：

> 页面 A 一大段 prompt
> 页面 B 一大段 prompt
> 页面 C 一大段 prompt

因为这会带来：

* 难维护
* 易重复
* 页面稍改就失效
* 无法复用

更建议这样做：

### 把页面上下文拆成四类数据

#### 1. 固定不变层

* 系统身份
* 智能体性格
* 回复风格
* 安全边界
* 工具调用规则

这部分长期稳定，适合固定 system prompt。若大量请求重复携带这类前缀，Prompt Caching 可以降低延迟和输入成本；OpenAI 官方文档说明它会对重复前缀自动生效。([OpenAI开发者][4])

#### 2. 用户层

* 用户角色：学生 / 教师 / 管理者
* 专业背景
* 学习阶段
* 历史表现
* 偏好语气
* 已掌握知识点

这部分不随页面变，但会随用户变化。

#### 3. 页面语义层

* page_id
* page_type
* course/chapter/section
* teaching_goal
* current_task
* related_knowledge_points
* common_misconceptions

这部分建议提前建模。

#### 4. 页面运行态层

* 当前打开的标签
* 当前图表参数
* 当前作答状态
* 当前实验进度
* 当前成绩/反馈
* 当前选中的知识点

这部分应在页面运行时采集。

## 四、页面动态感知具体怎么做

### 1. 路由感知

对于 SPA，监听：

* 前端路由切换事件
* `history.pushState`
* `history.replaceState`
* `popstate`

这些机制本身就是浏览器导航状态管理的基础。([MDN Web Docs][2])

### 2. DOM/组件变化感知

若页面内容不是路由切换，而是在同一路由下动态更新，可用：

* React/Vue 状态管理订阅
* 页面级事件总线
* `MutationObserver` 作为兜底监听

`MutationObserver` 可以监视 DOM 树变化，适合捕捉页面局部更新，但在工程上最好把它作为补充，而不是主数据源。([MDN Web Docs][3])

### 3. 页面上下文提取器

推荐给每类页面都实现一个统一接口，例如：

```ts
interface PageContextProvider {
  getStaticContext(): PageStaticContext
  getRuntimeContext(): PageRuntimeContext
}
```

例如：

* 知识页：提取标题、知识点、教学目标、正文摘要
* 练习页：提取题目、学生答案、错误点、解析状态
* 仿真页：提取参数、图形指标、操作历史
* 测验页：提取作答进度、得分、薄弱点

### 4. 唤起助手时组装上下文

用户点击助手按钮时：

1. 取固定系统 prompt
2. 取用户画像
3. 调当前页面 `getStaticContext()`
4. 调当前页面 `getRuntimeContext()`
5. 必要时检索知识库补充
6. 压缩成结构化 prompt

## 五、推荐的工程架构

### 推荐采用“混合式四层架构”

#### 前端

负责：

* 感知当前路由
* 感知当前页面状态
* 暴露 `getPageContext()`
* 发送结构化上下文到后端

例如：

```json
{
  "page": {
    "page_id": "root_locus_lab_01",
    "page_type": "simulation",
    "course": "自动控制原理",
    "chapter": "根轨迹",
    "teaching_goal": "理解增益变化对闭环极点和动态性能的影响"
  },
  "runtime": {
    "k": 4.5,
    "overshoot": 0.28,
    "settling_time": 3.1,
    "student_attempts": 2,
    "selected_focus": "减小超调"
  }
}
```

#### 后端 Context Orchestrator

负责：

* 合并系统 prompt、用户画像、页面上下文
* 判断是否需要知识库检索
* 做长度裁剪和优先级排序
* 输出最终模型请求

#### 知识库 / 元数据层

建议至少有三张表：

* `page_registry`
* `teaching_goal_registry`
* `knowledge_point_registry`

后续再扩展：

* `common_misconceptions`
* `recommended_scaffolds`
* `assessment_rubrics`

#### 大模型调用层

建议把 prompt 拆为：

* system：身份、规则、平台边界
* developer/application：平台任务约束
* context：用户 + 页面 + 检索结果
* user：用户当前问题

### 第一阶段：先落地 B

到这一步，助手就不是简单聊天机器人，而是**真正的平台级教学智能体**。

## 八、一个很实用的落地设计

你可以给每个页面定义一个最小上下文协议：

```json
{
  "page_id": "string",
  "page_type": "content|exercise|simulation|assessment|discussion",
  "course_id": "string",
  "chapter_id": "string",
  "section_id": "string",
  "teaching_goal": "string",
  "knowledge_points": ["string"],
  "current_activity": "string",
  "runtime_state": {},
  "ui_selection": {},
  "teacher_intent": "string"
}
```

然后所有页面都实现：

```ts
window.AIOBE_CONTEXT_PROVIDER = {
  getContext: async () => ({ ... })
}
```

助手弹窗一打开，就调用：

```ts
const ctx = await window.AIOBE_CONTEXT_PROVIDER.getContext()
```

这样你不用靠抓整页 DOM 来猜，而是由页面主动“自报家门”。

这是最工程化、最稳的方式。

## 九、一些容易踩的坑

### 1. 不要直接注入整页 HTML

噪声太大，token 浪费严重，而且容易把导航栏、按钮、无关说明一并塞进去。

### 2. 不要把“教学目标”完全靠模型猜

教学目标应来自你定义的课程结构，不应由模型自由推断。

### 3. 页面动态感知不要只靠 DOM 监听

`MutationObserver` 很适合做兜底，但更理想的是业务组件主动提供上下文，因为 DOM 变化不等于语义变化。([MDN Web Docs][3])

### 4. 固定提示词、用户画像、页面上下文要分层缓存

固定部分重复率高，适合长期复用；OpenAI 官方文档说明重复前缀会自动获得 Prompt Caching 带来的延迟和成本收益。([OpenAI开发者][4])

### 5. 上下文要做“压缩”和“优先级”

不要所有字段都永远发。
例如：

* 首先发教学目标
* 其次发当前活动
* 再发当前状态
* 最后才发补充信息

## 十、最终建议

你的问题的核心答案是：

**需要提前准备，但不是“每个页面写一大段固定上下文”，而是“为每类页面或每个教学节点建立结构化语义元数据”，再在助手被唤起时结合当前页面运行态动态注入。**

我给你的推荐顺序是：

**最佳实践路线：**

1. 先做页面路由感知
2. 每类页面实现 `getContext()`
3. 建立页面语义注册表
4. 后端做上下文编排
5. 再逐步引入 RAG 检索补充

如果只选一句话概括：

**最优方案不是“按页面存 prompt”，而是“按页面存语义元数据，按运行时组装上下文”。**
