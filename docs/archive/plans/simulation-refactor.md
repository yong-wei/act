这份 Codex 方案**作为“4-1 互动课程页的首个 Rust/Wasm 落地方案”是合理的，作为“整个项目统一仿真引擎方案”还不够完整。**原因很清楚：你现有项目已经有一条统一主干内核，包含固定步长时钟、Tustin 离散化、线性对象统一封装和纯延时处理；同时还并存 3D 船舶仿真主线、三域联动分析引擎、控制奥德赛等多条路线。而这份计划的 v1 数学范围只覆盖“连续时间 SISO 线性定常系统，不做时滞、离散系统、MIMO”，更准确地说，它是**控制分析内核**的重构计划，不是完整**仿真运行时内核**的统一计划。 

## 我对这份方案的总体判断

我给它的定位是：

**方向对，分层对，首案对；但边界还需要重新命名并补齐。** 

它做对的地方主要有四个。

第一，**Rust/Wasm + Web Worker + 前端图形面板** 这个分层是对的。因为你当前三域联动本来就是一套独立的控制理论计算引擎，而不是直接复用统一主干；把这类数值分析从前端 TS 中抽出来，是最自然、也最容易验证收益的一步。 

第二，**统一计算协议**是必要的，而且方案里把输入输出收成 `ComputeRequest / ComputeResult`，并明确图形族、指标族、闭环配置、采样配置、频率扫描范围、根轨迹扫描范围，这一点非常好。你现在项目的核心问题本来就不是“没法算”，而是“多套实现并存、口径难统一”。统一协议能直接解决这一点。 

第三，**Worker 封装成统一 hook** 很合理。`useControlEngine()` 统一管理生命周期、去抖、取消、缓存键、最新请求优先，这正适合互动课程里滑块频繁拖动、多图同步刷新的场景。方案里又明确“所有页面都通过 hook 取数，不允许页面各自直接调 Wasm”，这个约束非常关键。

第四，**4-1 作为首个接入案例**是合适的。因为它本质上是“控制分析图形面板”场景，和 3D 船舶仿真、控制奥德赛相比，边界更清晰、收益更容易验证、失败成本更低。

## 这份方案最大的不足

最大的不足不是技术选型，而是**它当前把“控制分析内核”写成了“统一仿真引擎”的样子。**

你现有项目里，统一主干已经承担了固定步长推进、对象离散化、纯延时、控制器与对象解耦；控制奥德赛已经直接接入 `createLinearPlant`，而且关卡里包含纯延时、双重积分、非最小相位、开环不稳定、高阶惯性链等对象。也就是说，项目现状已经超过了这份计划的 v1 能力边界。若按当前写法直接推进，最后得到的会是一套很强的“课程分析引擎”，但还不是一套真正能统一现有仿真主干的“运行时内核”。 

第二个不足是**前端图形路线还不够分层**。方案里默认图表统一走 ECharts Canvas 渲染，这对时域响应、幅相频、Nyquist 这类高密度曲线很合适；但如果未来要把这套公共层推广到更强交互的复平面编辑、根轨迹直接操控、极点零点拖拽、约束区交互，全部塞进 ECharts Canvas 会让“精细几何操控”变笨。4-1 这么做没有问题，但公共面板库最好从一开始就预留“ECharts 曲线层 + SVG 交互覆盖层”的能力，而不是把渲染路线锁死。

第三个不足是**“不保留示意图兜底分支”这个表述过于绝对。** 我同意不该保留第二套计算路径，否则会重新制造技术债；但课程页面最好保留**只读 fixture 回退**，也就是当 Worker/Wasm 加载失败时，至少还能展示基线静态结果和提示信息，而不是白屏。这个回退不参与计算，不构成第二条算法路径，只是教学内容降级显示。方案里已有 Octave fixture 基线测试，这正好可以拿来做只读回退。

## 我建议的综合方案

我建议把整个方案明确拆成**两层内核 + 一层图形工作台**，不要试图用一个 v1 同时覆盖全部目标。

### 第一层：Control Analysis Core

这就是 Codex 方案当前真正擅长的部分，也是**第一阶段应该做的东西**。

范围就按它现在的 v1 来，但名称要改准确：

* 连续时间 SISO 线性定常系统
* 传函块串并联与反馈
* 常见补偿族组合
* 时域响应、Bode、Nyquist、根轨迹、裕度指标
* Rust crate + Wasm
* Worker 异步调度
* `useControlEngine()` 统一入口
* 4-1 首次接入

这一层的目标是：**替换现有三域联动/互动课程中的控制分析计算路径。**
这一层我认为 Codex 的方案基本成立。

### 第二层：Simulation Runtime Core

这才是你前面一直在说的“统一仿真内核”。

它应当在第一层稳定后再做，能力至少要覆盖你当前主干已经存在的部分：

* 固定步长时钟
* Tustin 离散化
* 线性对象步进
* 纯延时缓冲
* 控制器逐步更新
* 状态空间直接输入
* 扰动/参考输入注入
* 结果采样与指标提取

这层的目标不是先服务 4-1，而是**替换 `src/lib/simulation` 的 TS 数值主干，并进一步给控制奥德赛复用。**
也就是说：

* **4-1 / 三域联动** 优先接第一层
* **控制奥德赛 / 统一主干** 优先接第二层
* **3D 船舶页面** 先保持 TS/React Three Fiber 页面壳不变，只在其线性子模块、控制器子模块逐步接入第二层

这样分层后，路径会清楚很多。

### 第三层：Control Chart Workspace

前端图形层不要简单理解为“换 ECharts”，而要做成**统一图形工作台**。

我建议图形层按下面方式设计：

* **Step / Magnitude / Phase / Bode / Nyquist**：ECharts Canvas
* **RootLocus / Pole-Zero / 复平面约束图**：ECharts 负责曲线和坐标轴，SVG overlay 负责可编辑元素
* **ControlChartPanel** 继续保留，但内部支持可选 overlay 插槽
* 所有面板只吃标准化数据，不做计算

这样 4-1 仍然可以全部只用 ECharts Canvas，因为它是阅读型页面；但公共库不会把未来互动能力封死。

## 一个更合适的实施顺序

我建议把原计划改成下面这个顺序。

### 阶段 A：按 Codex 方案落地 4-1

目标很单纯：

* 建 `rust/control-engine/`
* 建 `src/resources/control-system/`
* 上 Worker
* 上 `useControlEngine()`
* 上四类主图
* 用 Octave fixture 做一致性测试

这一步验证：

* 协议是否稳
* Wasm/Worker 是否顺
* ECharts 面板是否够用
* 结果是否贴近 MATLAB/Octave

这一步我完全赞成。

### 阶段 B：用同一内核替换三域联动现有计算层

把现在独立的 TS `linkage-engine` 迁到 Rust/Wasm，对外仍保留现有 React 页面和图形结构。

这一步完成后，你会第一次真正得到“互动课程公共分析内核”。这也是最容易看到收益的一步。

### 阶段 C：新建 Runtime 子模块，接管统一主干

在 Rust crate 中再补一个运行时子模块，专门承接：

* 固定步长
* 离散化
* 延时
* controller step
* plant step

然后先从**控制奥德赛**切入，因为它已经站在统一主干边界上，迁移最自然。

### 阶段 D：逐步渗透到 3D 船舶仿真

这里不要急着“全船模 Rust 化”。
先替换：

* 线性控制器
* 线性对象子模块
* 指标分析
* 参数扫描

至于 MMG 3DOF、船型专用环境扰动、复杂场景调度，继续在 TS 工程壳里组织，等 Runtime Core 稳定后再看是否拆出 Rust Native 服务端版本。

## 我建议对 Codex 方案做的三处具体修改

第一，把方案标题从“Rust Wasm 控制系统计算引擎与 4-1 图形面板改造计划”保留，但在摘要里明确补一句：

**“该计划是统一仿真内核的第一阶段，当前只覆盖控制分析核心，不覆盖仿真运行时核心。”**
这样团队不会误判边界。

第二，在统一协议里预留扩展字段，哪怕 v1 不启用，也要先留好：

* `delay`
* `discreteConfig`
* `stateSpaceSpec`
* `referenceProfile`
* `disturbanceProfile`
* `runtimeMode`

否则以后从分析内核扩到运行时内核时，接口会被迫破坏性升级。这个建议是结合你当前主干已支持纯延时与固定步长推进得出的。

第三，把图形面板体系从“统一 ECharts Canvas”微调成：

**“默认 ECharts Canvas，交互型复平面面板支持 SVG overlay。”**
这样 4-1 不受影响，后续公共层可持续演进。

## 最终结论

这份计划**不应该被否掉，应该被“重新定位 + 补齐分层”后直接推进。**

最准确的综合方案是：

```latex
\text{Phase 1: Control Analysis Core (Rust/Wasm + Worker + ECharts)}
\rightarrow
\text{Phase 2: Shared Interactive Course Engine}
\rightarrow
\text{Phase 3: Simulation Runtime Core}
\rightarrow
\text{Phase 4: Selective adoption in Control Odyssey and ship simulations}
```

一句话说：

**Codex 这份方案很适合作为“统一 Rust 重构”的第一块地基，但它现在只盖到了“分析内核”，还没盖到“仿真运行时内核”。你要做的不是推翻它，而是把它纳入一个更完整的双层内核路线。**
