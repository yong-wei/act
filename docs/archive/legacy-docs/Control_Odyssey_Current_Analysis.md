# Control Odyssey (控制奥德赛) - 现状深度分析

## 1. 物理引擎实现局限

通过对 `src/resources/interactive-learning/control-odyssey/engine/physics.ts` 和 `level-data.ts` 的代码审计，发现当前系统的物理实现与教学设计存在断层，导致部分高阶关卡无法达到预期的教学效果。

目前的 `PhysicsEngine` 仅实现了三种硬编码的差分方程，无法支撑 `level-data` 中规划的复杂传递函数。

| 引擎模式 | 当前代码实现逻辑 | 等效传递函数 (位置输出) | 教学概念偏差 |
| :--- | :--- | :--- | :--- |
| **PROPORTIONAL** | $\dot{y} = K \cdot u$ | $G(s) = \frac{K}{s}$ | 实际上是**积分环节**（0型系统被实现为1型），真正的比例环节应为 $y=Ku$。但作为位置控制，积分关系符合物理直觉。 |
| **INTEGRAL** | $\ddot{y} + D\dot{y} = K \cdot u$ | $G(s) \approx \frac{K}{s(s+D)}$ | 实际上是**惯性+积分**，而非纯双重积分 ($1/s^2$)。 |
| **INERTIAL** | $T\dot{v} + v = K \cdot u$ | $G(s) = \frac{K}{s(Ts+1)}$ | 正确实现了**积分+惯性**，但无法表现欠阻尼（震荡）特性。 |

## 2. 关卡设计与实现的脱节

在 `level-data.ts` 中，Level 8, 9, 10 被设计为二阶或高阶系统，但在 `simulation` 配置中被迫使用了 `engineType: 'INERTIAL'`。

*   **Level 8 (欠阻尼二阶)**: 配置了 `denominator: [1, 1.4, 1]` ($\zeta=0.7$)，但物理引擎只能执行一阶惯性逻辑。
*   **Level 9 (无阻尼二阶)**: 配置了 `denominator: [1, 0, 1]` ($\zeta=0$)，物理引擎同样无法表现出震荡。
*   **后果**: 这些关卡在游戏中表现得完全一样，都是平滑的一阶惯性曲线，**完全丢失了“超调”、“震荡”与“共振”这些核心控制特性**。

## 3. 缺失的关键对象

为了全面覆盖经典控制理论的主要问题，当前实现缺失了以下关键对象：

1.  **真正的二阶振荡环节**: 需要实现 $\ddot{y} + 2\zeta\omega_n \dot{y} + \omega_n^2 y = K u$。
2.  **非最小相位系统 (RHP Zero)**: 例如 $G(s) = \frac{1-s}{s(s+1)}$，表现为“反调”，是控制难点。
3.  **开环不稳定系统 (RHP Pole)**: 例如 $G(s) = \frac{1}{s(s-1)}$，表现为发散，展示反馈控制的镇定作用。

## 4. 结论

当前的物理引擎架构（基于特定物理含义的硬编码）限制了关卡设计的自由度。为了实现更丰富的教学目标，必须重构物理引擎，使其能够通用地求解任意传递函数（或至少是二阶及以上系统）。
