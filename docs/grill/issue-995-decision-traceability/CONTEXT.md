# Issue #995：决策记录可追溯性

该上下文统一功能需求从讨论、决策到实现提交之间的可追溯语言。

## 语言

**Grill 决策记录**：
围绕一个需求形成、经确认并可被后续审阅的决策问题、选项、依据和结论集合。它是实现的输入证据，不是一次性对话摘要。
_避免：会话记忆、临时笔记、未提交的讨论记录_

**任务决策目录**：
以单个需求或变更为边界保存其 `CONTEXT.md` 与 ADR 的独立目录，避免不同任务写入同一文件而产生冲突。
_避免：共享的全局决策草稿、按日期混合多个需求的目录_

**任务标识**：
任务决策目录的稳定名称：有 GitHub Issue 时为 `issue-<number>-<slug>`，无 Issue 时为 `local-<YYYYMMDD>-<slug>`。
_避免：随机 UUID、仅由标题构成且不标识来源的名称_

**实现 PR**：
同时包含该需求的决策记录、计划或 OpenSpec 产物与代码实现的拉取请求，使审阅者能够追溯实现依据。
_避免：只包含代码的 PR、事后补充而无关联的文档提交_

**集成 PR**：
目标分支为 `integration` 的实现 PR；它在创建后请求已配置的 Codex 审查。目标为 `main` 的 PR 必须在审查前更正。
_避免：直接面向 main 的常规实现 PR、沿用范围过大的旧审查请求_

**交付校验**：
本地提交阶段验证任务清单存在且结构有效，PR 阶段验证该任务清单覆盖整条变更范围的双层约束。
_避免：把同一 PR 误解为同一提交、只依赖单一阶段的检查_

**Use-Grill-Me 包装链路**：
调用 Grill-with-Docs 前读取既有任务决策目录、相关上下文和 ADR，并将新的结论写回当前任务决策目录的项目约定流程。
_避免：直接运行未感知项目决策记录的原生 Grill-with-Docs_

**任务清单**：
位于任务决策目录的 `manifest.json`，显式关联决策记录、OpenSpec 变更（如有）与实现范围，作为提交校验的唯一输入。
_避免：通过代码路径猜测任务边界、共享的全局任务登记表_

**实施计划**：
没有 OpenSpec 变更的任务在任务决策目录保存的 `plan.md`；有 OpenSpec 变更时，由任务清单关联 change 目录中的计划和任务。
_避免：仅留在会话中的计划、同时维护两套计划真源_
