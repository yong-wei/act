# 20260729-am 访谈域词汇

## 备课知识点本地覆写

教师在备课侧对规范化知识概念的一次性表述调整，用于适配特定班级的认知水平或教学需要。

**约束：**
- 覆写仅存在于备课侧，不同步回知识基座
- 知识基座保持规范化概念的真实性
- 同一知识点在不同班级允许多个本地覆写

**代价：**
- 跨班级学情分析和资源复用失去统一语义锚点
 
 ## 课件资源-知识关联冻结
 
 课件发布后，其内部资源与知识概念之间的绑定关系冻结在发布时刻的教案修订版 ID 和版本号上。
 
 **约束：**
 - 后续教案修订版中新增或删除的知识点引用，不影响已发布课件的既有绑定
 - 教师若需更新绑定，必须基于新版教案主动执行"重发"操作，产生新的课件版本号
 - 旧课件保留旧绑定和旧教案版本映射
## 控制引擎作为课件标准分析能力

控制引擎（control-engine WASM）是互动课件内容可编排的标准仿真与分析能力，教师编辑课件时可直接插入由其驱动的活动模块（如频域分析、根轨迹观测、PID 参数调整等）。

**约束：**
- 引擎与课件活动模块之间的接口定义合约版本
- 引擎的 WASM 编译和版本管理纳入课件发布管线的依赖项
- 不要求每个课件活动都使用引擎，但引擎提供的能力属于平台标准运行时

**设计含义：**
- control-analysis-service.ts 作为课件运行时的共享服务模块
- 互动课件活动类型扩展"仿真执行"类别
- 引擎版本升级需与课件发布门禁协同，避免已发布课件的运行时不兼容
## AI 审核报告与发布门禁的关系

AI 审核报告是教师按需发起的质量检查工具，不直接作为发布门禁条件。

**机制：**
- AI 审核发现来源覆盖缺口 → 教师通过"来源缺口确认"机制显式处理（确认或填补）
- 发布门禁检查的是缺口是否已被教师处理过（confirmed 或 filled），而非 AI 报告的结论值
- 门禁保持确定性可重复：不依赖 AI 模型版本或阈值

**原理：**
- 门禁必须由确定性程序执行
- AI 审核结论随模型版本变化，不具备确定性
- 教师的人工确认决策是发布门禁的可依赖锚点
## 学情诊断的基本单位

**诊断单位：** 规范化知识节点（KnowledgeProgress），六维能力向量为跨节点的聚合视角。

**依据：**
- 教学干预的最小粒度是知识节点
- KnowledgeProgress（progress 0-100, status: NOT_STARTED/IN_PROGRESS/COMPLETED）已覆盖逐节点进度
- 六维能力向量适合班级级对比和趋势分析，不足以定位具体教学行动

**限制：**
- 知识图谱中未被 KnowledgeProgress 覆盖的节点不出现在诊断结果中
- 不允许教师自定义诊断维度（与规范化知识基座的约束冲突）
## 诊断触发机制

**模式：** 事件驱动——教师在助教界面点击"生成诊断"时触发。
**排除：** 定时批量快照不作为学情诊断的触发方式。

**范围限制：**
- 无背景 pipeline → 教师不会收到主动预警
- 需要前置指标让教师感知"需要诊断了"
 
 ## 风险标记后台扫描
 
 保留轻量的被动式后台 pipeline，仅用于产生 StudentRiskFlag，不做能力向量计算或诊断报告生成。
 
 **规则引擎特征：**
 - 确定性规则（非 AI 模型），如连续 N 次低于阈值、连续 M 天未登录
 - 只写 StudentRiskFlag 表
 - 风险标记作为教师仪表盘的被动指标，诱导教师点击"生成诊断"
 
 **与事件驱动诊断的关系：**
 - 风险扫描：后台被动执行 → 产生风险标记 → 仪表盘展示
 - 诊断报告：教师主动触发 → 基于当前数据和风险标记 → 生成完整分析
 
 ## 诊断报告层次
 
 诊断报告输出分为两个层次：
 
 **班级级：** 整体薄弱知识点分布、能力趋势、风险学生列表 → 教师备课参考
 **学生级：** 个体知识图谱薄弱点、错题归因、学习行为异常 → 教师个别辅导
 
 知识点级作为学生级报告的支撑细节嵌入，不独立输出。诊断产出不包括知识点级独立报告，以避免 N×M 信息过载。
 
 ## 诊断报告生成架构
 
 诊断报告作为 Konling TA 的一个特化 mode 生成，复用已有的 agent session 和 tool runtime 框架。
 
 **含义：**
 - 诊断报告生成继承 Konling 的权限、引用源治理和 citation guard 机制
 - 诊断过程可能涉及多轮工具调用（查快照、查风险标记、查知识点进度）
 - 结构化报告输出由 AI 模型生成后持久化，不在 agent session 中长期保留
 - 诊断 API 是诊断 mode 的入口，而非独立的后端服务
 
 ## 诊断 mode 工具集
 
 诊断 Konling mode 的专有工具，仅负责数据获取，分析归因由模型在上下文中完成。
 
 - `get_student_risk_flags` — 获取某学生/班级当前风险标记
 - `get_class_competency_summary` — 获取班级级能力聚合
 - `get_student_knowledge_progress` — 获取学生逐知识点掌握度
 
 **排除：** 分析性工具（weak area identification, session history）合并为模型上下文推理，不另设 tool。
 
 ## 诊断报告持久化
 
 诊断报告独立存储到诊断报告表（新表或扩展 StudentSessionReport），内容为结构化 JSON。
 
 **机制：**
 - Konling mode 负责"生成"动作，输出结构化内容
 - 生成完成后将结构化内容写入数据库
 - 后续查看从数据库读取，不再经过 AI 模型
 - Konling mode 不作为诊断历史的查看入口
 
 **设计理由：**
 - 支持不同时间点诊断报告的对比
 - 避免模型温度参数导致的输出不一致
 - 便于仪表盘渲染图表和趋势线
 
 ## 诊断到行动的闭环
 
 诊断报告不直接触发教学动作，仅提供指向性链接到备课工作台的对应知识点位置。
 
 **边界：**
 - 诊断回答"哪里有问题"
 - 备课回答"怎么调整"
 - 教师在教学备课上下文中自行决定调整方式
 
 **排除：**
 - 不自动生成补充练习
 - 不自动调整教案深度
 - 不绕过教师对教学内容的审核
