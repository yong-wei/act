从 `integration` 分支看，当前实现已经不再是早期“竞技场页面 + 多表征工作台”的状态，而是进入了一个可用的统一体系雏形。现在已经有 `/interactive-learning/control-workbench` 统一入口，路由会解析 `arenaTask / publicationId / preset / mode / objectId` 并交给统一工作台 shell。 竞技场任务也已经基本改为进入综合控制工作台，除 Control Odyssey 外，`workspace-routing.ts` 会把任务统一导向 `/interactive-learning/control-workbench?arenaTask=...&preset=...`。

这说明你“不要那么多工作台，用统一工作台降低认知负担”的方向已经被实现了一部分。当前系统已经有综合工作台 shell、对象选择、面板实例、视图配置、经典白箱四联图、黑箱辨识、复合校正、预测控制等预设。 经典白箱预设也不是另起炉灶，而是把原多表征联动工作台嵌入统一工作台中，保留原串联校正体验。

所以当前的主要问题已经不是“有没有统一入口”，而是：

**这个统一入口还更像“把多个工具装进同一个外壳”，尚未完全成为一个能持续训练学生、激发竞技意识、展示设计能力的控制系统设计场。**

下面我按理念和功能层面分析差距。

---

# 一、当前系统已经具备的基础

## 1. 竞技场的理念基础是正确的

`docs/arena.md` 中的原则仍然成立：竞技场不是某一种校正工具，而是统一评测与排行榜层；基本单元不是单纯对象，而是“对象 + 任务 + 允许方法 + 评测协议 + 榜单规则”。

这点非常关键。它决定了竞技场不应该服务于某一个章节、某一种校正方法，而应该成为控制设计能力的长期训练场。

## 2. 综合控制工作台的入口已经建立

当前 `/interactive-learning/control-workbench/page.tsx` 会解析：

```text
arenaTask
publicationId
classId
seasonId
preset
mode
objectId
```

并调用 `resolveControlWorkbenchSession` 构建工作台上下文。 这说明统一工作台已经有了“上下文驱动”的雏形。

## 3. 工作台已经支持多种预设

当前 session resolver 已经把不同任务映射到不同工作台预设：

```text
multi-representation-linkage -> classic-whitebox
block-diagram-workbench -> composite-control
predictive-control -> predictive-control
black-box-identification -> blackbox-identification
free-explore -> free-explore
```

同时根据任务类型给出不同允许视图。

这说明工作台已经不是单纯串联校正工具，而开始变成“统一外壳 + 预设模式”。

## 4. 视图配置系统已有雏形

当前 `views/index.ts` 已经定义了工作台视图插件，包括：

```text
time-domain
bode
root-locus
nyquist
experiment-dataset
identification
response-comparison
control-effort
metric-summary
```

并且针对不同视图提供可选项，例如时域响应中的参考输入、未校正输出、校正后输出，Bode 图中的未校正开环、校正后开环、校正装置，黑箱中的实验数据集、学生名义模型、虚拟预演响应等。

这基本吻合你提出的“每个视图有自己的配置菜单”的方向。

## 5. 黑箱辨识链路已经进入统一工作台

黑箱预设中已经能运行黑箱实验、生成数据集、保存学生名义模型、运行虚拟仿真预演，并提交黑箱官方评测。它也明确标注学生名义模型只用于工作台分析、预演和控制器草稿，不代表官方隐藏对象。

这是一个很好的方向，因为它把“辨识—名义模型—控制器—预演—提交”放入了统一工作台。

## 6. 复合校正和预测控制也有预设

复合校正预设已经提供前置滤波、前馈通道、局部反馈、扰动补偿等参数，并生成复合校正控制器数据。 预测控制预设也提供 MPC 或优化 PID 参数，并通过统一提交通道进入官方评测。

这说明系统已经从“经典控制工具”扩展到“多控制方法工具箱”。

---

# 二、和目标体系相比的核心差距

当前实现已经有统一工作台，但如果目标是让学生“磨炼各类控制系统设计、展现风采、提升竞争意识”，还差几个层面的建设。

我把差距分成七类。

---

## 差距 1：当前更像“工具集合”，还不像“训练体系”

现在的竞技场和工作台已经能让学生做事情，但它还没有足够明确地回答：

```text
学生为什么要反复挑战？
他在每次挑战中练什么能力？
他的能力如何成长？
他如何看到自己比上次更强？
他如何和别人比较，又如何从别人身上学习？
```

现在的任务、榜单、提交和工作台是分散存在的。它们组成了一个功能系统，但还没有形成一个清晰的“训练路径”。

一个完整的控制竞技体系应该像“控制设计道场”：

```text
入门任务：稳定、稳态误差、基本 PID
基础任务：超调、调节时间、裕度
进阶任务：串联校正、扰动抑制、能耗约束
工程任务：复合校正、限幅、鲁棒性、多场景
黑箱任务：辨识、名义模型、真实对象验证
高级任务：MPC、优化、约束控制
开放任务：自由方法、榜单竞技、方案展示
```

现在系统有这些任务类型，但学生端还没有强烈感受到“我正在沿着一条控制能力成长路径推进”。

---

## 差距 2：统一工作台已经有，但“模式感”仍偏弱

现在综合工作台 shell 会显示会话状态、对象选择、面板配置、预设面板等。 但从体验角度看，它仍更像一个工程化容器，而不是一个强引导的控制设计环境。

学生进入后需要理解很多概念：

```text
预设
面板
对象选择
允许方法
提交策略
视图实例
名义模型
官方目标
工作模型
```

这些概念对开发者合理，但对学生而言会有认知负担。

需要进一步把工作台分成三种学生可理解的状态：

```text
挑战模式：我正在完成一个官方挑战
探索模式：我在自由试验对象和方法
复盘模式：我在分析一次提交为什么好/坏
```

现在系统有 `challenge / explore / assignment / odyssey` 等 session mode，但界面上的学习语义还需要更突出。学生应该首先感知到“我现在在做什么”，而不是“我处在哪个技术 preset”。

---

## 差距 3：视图配置已有，但视图还没有完全服务“控制设计推理”

当前视图系统已经能配置选项，但它主要是在选择“显示什么曲线”。下一步要让视图成为“设计推理证据”。

例如时域视图不应只是显示响应曲线，而应支持学生理解：

```text
我牺牲了多少控制能量换来响应速度？
扰动进入后，输出多久恢复？
控制量是否逼近限幅？
名义模型与黑箱对象偏差有多大？
复合校正中前馈和反馈各自贡献了什么？
```

Bode 图也不应只是画幅频相频，而应回答：

```text
相角裕度变化说明了什么？
带宽提高是否带来噪声放大风险？
校正器到底把哪一段频率“抬起来”或“压下去”？
```

根轨迹也不应只是显示轨迹，而应强调：

```text
当前闭环极点落在哪里？
为什么这个增益会导致超调或不稳定？
校正器零极点如何改变极点迁移路径？
```

现在 `views/index.ts` 的配置项是必要基础，但仍缺少“解释层”和“诊断层”。

---

## 差距 4：竞赛氛围还不够强

一个真正能提升竞争意识的竞技场，不只是有榜单，还要有“赛制感”。

目前系统有提交、榜单、发布、班级上下文和任务详情。挑战详情页展示任务、模型、评价规则、榜单摘要，并将学生引导进工作台。 这已经是基本竞技结构。

但它还缺少更强的竞技机制：

```text
个人最佳成绩
本周挑战
班级挑战赛
赛季榜
连胜/连通关
首次稳定奖
最低能耗奖
最快响应奖
最佳改进奖
Pareto 前沿展示
同一任务不同方法榜对比
优秀方案展示墙
挑战复盘页
```

学生“展现风采”不是只看一个分数。控制设计有很多风格：

```text
有人响应快；
有人超调小；
有人能耗低；
有人鲁棒性强；
有人黑箱辨识好；
有人方案简单优雅；
有人从失败改进到成功。
```

当前榜单体系如果只突出综合分，会压扁这些风格。

---

## 差距 5：挑战任务还没有形成“能力地图”

竞技场要成为训练体系，需要把任务和能力关联起来。

例如每个任务可以明确锻炼：

```text
稳定性判断
稳态误差设计
频域裕度理解
根轨迹设计
PID 参数调试
串联校正设计
抗扰控制
控制能量意识
模型辨识
黑箱验证
约束控制
MPC 预测思想
```

现在 `docs/arena.md` 已经强调对象、任务、方法、指标、榜单的分层。 但学生端还需要看到“能力地图”。否则挑战只是一个个卡片，而不是一套成长体系。

理想状态是：

```text
你已掌握：闭环稳定、基本 PID
薄弱项：控制能量、相角裕度
推荐挑战：积分对象低频平衡、二阶对象超前校正
下一阶段：复合校正抗扰挑战
```

这会把竞技场从“比赛”升级为“能力训练”。

---

## 差距 6：黑箱和虚拟仿真仍偏“流程可用”，尚未充分体现工程真实性

黑箱工作台已经有实验、数据集、名义模型、预演和提交。 但功能体验仍偏模板化：

```text
运行实验
保存名义模型
填控制器参数
预演
提交
```

要真正体现工程感，需要强化几个体验点：

```text
实验设计是有代价的；
辨识模型是有误差的；
名义模型和真实对象会偏离；
控制器在名义模型上好，不等于在真实对象上好；
隐藏场景考察鲁棒性，而不是公开场景刷分；
预演结果只是预演，不是正式评测。
```

这些原则现在有部分文案，但还不够成为学生体验的核心。

黑箱挑战最适合培养工程意识。如果做得好，它能明显区别于普通题库。

---

## 差距 7：教师发布已经有，但“课堂/作业/竞技”的边界还需产品化

教师端已经可以发布 Arena 挑战，也能设置班级、可见性、截止时间、榜单策略、作业绑定等。 这是很重要的基础。

但教师端当前更像“配置台”，还不像“教学组织工具”。教师真正需要的是：

```text
我该给这节课发布哪个挑战？
这个挑战适合哪类学生？
作业截止前学生完成情况如何？
谁没有提交？
谁一直不稳定？
谁能耗过高？
谁有优秀方案可以课堂展示？
这个挑战是否暴露了某个知识点薄弱？
```

换句话说，教师端不仅要能发布，还要能组织、诊断、反馈和展示。

---

# 三、我建议的目标形态

如果要让它真正成为“学生磨炼控制设计、展现风采、提升竞争意识”的完整体系，目标不应只是“功能更多”，而应是五个子系统合在一起。

---

## 1. 训练体系：让学生知道自己在练什么

每个挑战都要有能力标签：

```text
稳定性
稳态误差
动态性能
频域裕度
串联校正
复合校正
抗扰
能耗
辨识
鲁棒性
约束控制
MPC
```

挑战卡片不仅显示任务名称，还要显示：

```text
推荐前置能力
本任务训练能力
难度等级
适合课程阶段
是否作业
是否开放榜单
是否隐藏测试
```

这样学生进入竞技场时不是盲目挑题，而是进入一张“控制设计能力地图”。

---

## 2. 设计体系：统一工作台成为真正的控制设计环境

综合工作台应继续坚持统一入口，但体验上要更像“控制设计 studio”。

建议工作台分成：

```text
任务栏：我在解决什么挑战
对象栏：我面对什么对象
方法栏：我正在使用什么控制方法
证据栏：我的设计证据是什么
提交栏：我的方案是否达到官方标准
复盘栏：我下一步该改哪里
```

现在的“面板配置”是必要能力，但学生更需要的是“设计流程”。

典型流程可以是：

```text
认识对象
选择方法
观察未校正表现
设计控制器
比较校正前后
检查约束
提交官方评测
复盘改进
```

黑箱流程则是：

```text
设计实验
采集数据
建立名义模型
验证名义模型
设计控制器
预演真实对象
提交隐藏评测
复盘模型误差
```

---

## 3. 评测体系：让学生相信榜单是公平的

Arena 当前官方评测已经较规范，白箱 PID/串联已接入分析评测链路。 但学生端还需要把“评测公平性”讲清楚。

应该明确展示：

```text
工作台预评测：用于调试
官方评测：用于榜单
隐藏场景：用于防止刷公开场景
硬约束：未通过不排名
协议版本：本次评分口径
```

尤其黑箱挑战，必须强调：

```text
预演不等于正式成绩
名义模型不等于真实对象
实验次数过多会产生代价
隐藏场景考验泛化能力
```

这样学生才会理解控制设计不是“刷参数”，而是“设计可泛化方案”。

---

## 4. 竞技体系：让学生有展示和竞争动力

我建议加入多层竞技机制。

第一层是个人成长：

```text
个人最好成绩
最近一次提交
历史提升曲线
首次通过
连续改进
失败到成功
```

第二层是班级竞技：

```text
班级榜
小组榜
作业挑战达标率
课堂展示榜
```

第三层是开放竞技：

```text
全站榜
赛季榜
方法榜
指标榜
Pareto 榜
```

第四层是荣誉体系：

```text
稳定性入门者
PID 调参能手
频域校正高手
低能耗设计奖
黑箱辨识达人
鲁棒控制挑战者
Pareto 前沿方案
```

这比单一排行榜更能承载“展现风采”。

---

## 5. 复盘体系：让比赛变成学习

竞技场不能只告诉学生“你第几名”。它应该告诉学生：

```text
为什么你没有进榜？
哪个硬约束失败？
哪个指标拖累分数？
你比上一次好在哪里？
你与榜首差距在哪？
你的方案风格是什么？
下一步建议改什么？
```

这会让竞技场既有竞争，又不会变成盲目刷榜。

---

# 四、整改方案：按功能和理念分阶段推进

下面只给功能层面的整改，不写代码和接口细节。

---

## 阶段 1：把竞技场从“任务列表”升级为“能力训练地图”

### 目标

让学生进入竞技场后，不只是看到挑战卡片，而是看到自己的控制设计成长路径。

### 功能整改

1. 给每个挑战增加明确能力标签：

```text
稳定性
动态性能
稳态误差
频域裕度
根轨迹
PID
串联校正
复合校正
辨识
黑箱
约束
MPC
鲁棒性
能耗
```

2. 按训练路径重组竞技场大厅：

```text
基础稳定挑战
PID 与参数调优
根轨迹与串联校正
频域裕度挑战
复合校正与抗扰
黑箱辨识与虚拟仿真
MPC 与高级方法
开放竞技挑战
```

3. 每个挑战卡片展示：

```text
训练目标
推荐前置能力
挑战难度
可用方法
官方评测类型
当前个人最好成绩
班级/全站排名摘要
```

4. 增加“推荐下一挑战”：

```text
如果学生稳定性未过，推荐基础稳定任务；
如果超调高，推荐阻尼与相角裕度任务；
如果能耗高，推荐低能耗控制挑战；
如果黑箱模型偏差大，推荐辨识任务。
```

### 验收标准

```text
学生能知道自己该从哪里开始；
教师能按课程章节选择挑战；
挑战不再只是散列表，而是能力地图。
```

---

## 阶段 2：把综合工作台从“容器”升级为“设计流程引导”

### 目标

统一工作台不仅能装载视图，还要引导学生完成控制设计过程。

### 功能整改

1. 顶部增加“当前设计流程状态”：

```text
对象分析
控制器设计
性能比较
约束检查
官方提交
复盘改进
```

2. 不同预设有不同流程：

白箱串联：

```text
看未校正响应 -> 观察根轨迹/频域 -> 调整控制器 -> 比较 -> 提交
```

复合校正：

```text
确认控制结构 -> 设置前馈/反馈/扰动补偿 -> 看输出与控制量 -> 检查能耗 -> 提交
```

黑箱：

```text
运行实验 -> 保存名义模型 -> 设计控制器 -> 虚拟预演 -> 官方评测
```

MPC：

```text
设置预测参数 -> 检查约束 -> 看控制量 -> 提交模板评测
```

3. 面板配置继续保留，但隐藏在“高级配置”里。默认状态下，学生应看到最适合当前任务的视图组合，而不是先面对大量选项。

4. 对不支持的视图，不只是禁用，而是解释控制理论原因：

```text
黑箱对象不公开模型，因此无法显示官方对象 Bode 图；
非串联结构不适合根轨迹解释；
MPC 的关键证据是约束与预测轨迹，而不是校正器零极点。
```

### 验收标准

```text
学生进入工作台后能自然知道下一步做什么；
工作台不是工具堆，而是设计流程；
高级学生仍可展开配置。
```

## 阶段 3：强化视图的“设计证据”功能

### 目标

让图表不只是画图，而是帮助学生证明自己的设计是合理的。

### 功能整改

1. 时域视图增加设计证据解释：

```text
超调变化
调节时间变化
稳态误差变化
控制量峰值
扰动恢复时间
名义模型与真实对象误差
```

2. Bode 图增加频域解释：

```text
相角裕度变化
幅值裕度变化
交越频率变化
带宽变化
高频放大风险
```

3. 根轨迹图增加闭环极点解释：

```text
当前闭环极点位置
主导极点
极点移动趋势
可能导致超调/不稳定的原因
```

4. 黑箱辨识视图增加模型可信度解释：

```text
数据质量
实验覆盖度
名义模型误差
该模型是否足以用于控制器设计
```

5. 复合校正视图增加分量解释：

```text
前馈改善了什么
反馈抑制了什么
扰动补偿贡献了什么
控制量是否过大
```

### 验收标准

```text
每个视图都能回答“这个图说明了什么”；
学生可以基于图表说清自己的设计理由；
教师可以用这些视图组织课堂展示。
```

## 阶段 5：把官方评测解释产品化

### 目标

让学生理解官方评测，而不是只看到一个分数。

### 功能整改

1. 提交结果页显示：

```text
是否通过硬约束
每个硬约束状态
每个排名指标满意度
总分构成
惩罚项
协议版本
是否隐藏场景
```

2. 对未通过提交给出明确原因：

```text
闭环不稳定
控制器参数非法
响应发散
控制能量超限
隐藏场景失败
黑箱实验数据不属于当前学生
```

3. 对通过提交给出改进建议：

```text
若想冲击更高排名，优先降低控制能量；
当前超调较小，但调节时间偏长；
当前模型拟合较好，但隐藏扰动下恢复较慢。
```

4. 显示“与个人最好成绩对比”：

```text
分数提升 / 下降
调节时间变化
超调变化
能耗变化
稳态误差变化
```

### 验收标准

```text
学生知道为什么得这个分；
学生知道下一次应改什么；
教师能用结果页讲评。
```

## 阶段 6：把黑箱挑战做成工程意识训练

### 目标

黑箱挑战不只是填几个参数，而是训练实验设计、辨识、鲁棒性和工程验证。

### 功能整改

1. 黑箱任务分为四个明确步骤：

```text
实验设计
名义模型建立
控制器设计
真实对象验证
```

2. 实验设计要显示预算与代价：

```text
每次实验消耗预算
剩余预算
实验信号覆盖程度
数据质量
```

3. 名义模型要显示可信度：

```text
拟合质量
数据覆盖范围
与黑箱响应偏差
是否建议用于控制器设计
```

4. 预演与官方评测分开显示：

```text
虚拟预演：公开场景，自我检查
官方评测：隐藏场景，正式排名
```

5. 提交后反馈模型泛化问题：

```text
名义模型上表现好，但隐藏场景失败；
控制能量过高；
扰动恢复慢；
实验次数不足或数据质量低。
```

### 验收标准

```text
学生能体验“模型不等于真实对象”；
黑箱任务体现工程控制思维；
刷参数行为被弱化。
```

# 五、优先级建议

如果按“最能提升学生磨炼与竞争意识”排序，我建议下一阶段优先级是：

```text
1. 训练路径与能力地图
2. 工作台设计流程引导
3. 提交结果解释与个人改进反馈
4. 多层榜单与荣誉机制
5. 教师讲评与发布报告
6. 黑箱工程意识强化
7. 学生成长画像与推荐
```

原因是：当前基础设施已经比较强，下一步真正短板在“学生为什么愿意反复来挑战、教师为什么愿意用它组织教学、挑战如何转化为能力成长”。

# 六、最终判断

从 `integration` 分支看，当前系统已经完成了“统一工作台 + Arena 评测层”的关键基础。它已经不再是零散工具，也不再完全绑定串联校正。

但如果要成为完整体系，还需要从“功能可用”升级到“训练可感、竞争可见、成长可追踪、讲评可组织”。

当前系统的状态可以概括为：

```text
基础设施：较强
统一入口：已建立
白箱经典控制：较成熟
黑箱辨识：已有流程
复合/MPC：有模板预设
教师发布：已能用
竞技氛围：还不够强
能力成长路径：还不够清晰
复盘反馈：还不够深
优秀方案展示：还没形成体系
```

所以整改方向不应再只是“继续加功能”，而应围绕一个产品目标收敛：

**把 Arena 做成控制系统设计训练场，把综合工作台做成控制设计 studio，把榜单做成多维风采展示，把评测结果做成学习反馈。**
