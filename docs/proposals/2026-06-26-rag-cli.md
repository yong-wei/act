# Pro reply 1:
这个想法值得做，但我不建议把它做成“一个独立 CLI 检索脚本”。更合理的是：

**抽出一个统一的 retrieval/source-pack 核心库，CLI 只是其中一个调用外壳；服务器端控灵、路径规划、Codex/技能写讲义都调用同一套检索核心和同一种 Source Pack 协议。**

这样可以避免三套检索逻辑分裂：一套给 RAG，一套给路径规划，一套给讲义生成。你现在项目里已经有资源治理、ResourceSegment、CitationTarget、RetrievalChunk、runtime projection、PlanningUnit eligibility 这些基础，不应该绕开它们重新扫 md 文件。最近的资源摄入 PR 已经把媒体 manifest 投影到 `ResourceSegments`、`CitationTargets`、`RetrievalChunks`，并强调不直接授予路径 eligibility；这正是 Source Pack 的底层素材层。 另一个 runtime projection PR 也已经把 sidecar、PlanningUnit 生成、人审、source hash/version、stale review 等约束接到了资源路径里。

所以要做的不是“CLI 解析教科书 md 并返回若干段落”，而是做一个**面向项目资源治理体系的 Source Pack Builder**。

## 1. Source Pack 的定位

Source Pack 不应该是“检索结果列表”，而应该是一个可审计、可复现、可权限过滤、可被不同智能体消费的中间证据包。

它至少服务三类场景：

**讲义/课程内容制作**：偏权威性和覆盖面，需要教材、参考书、论文、图表说明、公式出处、章节结构、概念边界。它可以返回较宽的 source pack，但不能把整章内容塞给模型。

**控灵问答**：偏即时回答和学生可见性，需要短小、明确、可引用的证据片段，必须严格过滤 `student-visible` 权限，不能把教师态、管理态、未审核资源泄露给学生。

**路径规划**：偏资源节点与学习目标匹配，需要知道哪些资源可作为 `PlanningUnit`，哪些只是引用/检索素材，哪些只适合教师备课，不适合推给学生。这里不能只按语义相关性排序，还要考虑图谱节点、能力目标、难度、预计用时、路径 eligibility、资源状态和人审状态。

因此，Source Pack 的核心字段应类似：

```ts
export interface SourcePack {
  packId: string;
  profile: "handout-authoring" | "konling-answer" | "path-planning" | "lesson-design" | "assessment-item";
  query: SourcePackQuery;
  indexRefs: {
    retrievalIndexVersion: string;
    resourceProjectionVersion?: string;
    graphCatalogVersion?: string;
    objectiveCatalogVersion?: string;
    generatedAt: string;
  };
  coverage: {
    knowledgeNodeIds: string[];
    capabilityTargetIds: string[];
    qualityTargetIds: string[];
    learningGoalIds: string[];
    sourceTypes: Record<string, number>;
    modalityTypes: Record<string, number>;
    missingCoverage: string[];
  };
  items: SourcePackItem[];
  limitations: SourcePackLimitation[];
}
```

每个 `SourcePackItem` 应该保留稳定引用，而不是只保留文本：

```ts
export interface SourcePackItem {
  itemId: string;
  resourceNodeId?: string;
  planningUnitId?: string;
  retrievalChunkId: string;
  citationTargetId: string;

  title: string;
  sourceKind: "textbook" | "reference" | "paper" | "handout" | "image" | "audio" | "video" | "runtime-lesson" | "knowledge-card";
  modality: "text" | "equation" | "figure" | "table" | "image-description" | "audio-transcript" | "video-transcript";

  excerpt: string;
  whyIncluded: string;

  authorityScore: number;
  relevanceScore: number;
  graphAlignmentScore: number;
  eligibilityScore: number;
  finalScore: number;

  citation: {
    label: string;
    sourceTitle: string;
    chapter?: string;
    section?: string;
    page?: string | number;
    figureId?: string;
    equationId?: string;
    objectKey?: string;
    hash?: string;
  };

  access: {
    visibility: "student-visible" | "teacher-scoped" | "admin-scoped";
    license?: string;
    aiUsePermission: "allowed" | "restricted" | "blocked";
  };
}
```

关键点是：**Source Pack 里出现的每一条材料都必须能回到 `CitationTarget`，而不是回到一个不稳定 URL 或 md 行号。**

## 2. CLI 可以做，但 CLI 应该是薄壳

CLI 的价值很明确：Codex、技能、本地作者态工作流都可以按需调用，不需要 MCP 长期驻留上下文；CLI 还可以把大结果写成文件，只把 pack 摘要返回给主线程。

但 CLI 不应该直接承担业务逻辑。建议结构是：

```text
src/lib/source-pack/
  source-pack-types.ts
  source-pack-builder.ts
  hybrid-retriever.ts
  retrieval-profiles.ts
  citation-hydrator.ts
  pack-ranker.ts
  pack-diversifier.ts
  pack-serializer.ts

scripts/source-pack/source-pack-cli.ts
```

服务器端控灵调用：

```ts
import { buildSourcePack } from "@/lib/source-pack/source-pack-builder";
```

本地/Codex/技能调用：

```bash
npm run source-pack -- build \
  --profile handout-authoring \
  --query "频率响应法中相角裕度与系统稳定性的关系" \
  --course automatic-control \
  --top-k 120 \
  --pack-size 18 \
  --out .source-packs/frequency-margin.pack.json
```

也就是说：

```text
同一个 buildSourcePack()
  ├─ CLI 调用
  ├─ 控灵 API 调用
  ├─ 路径规划调用
  └─ 讲义生成技能调用
```

这比“CLI 一套、服务端 RAG 一套”更稳。否则后期一定会出现：Codex 讲义引用的材料，控灵检索不到；路径规划生成的资源节点，讲义制作工具无法解释；本地 CLI 的权限规则和服务器控灵不一致。

## 3. 检索流程建议

建议采用五阶段 pipeline。

### 阶段一：Query normalization

输入不只是自然语言 query，还应该允许带上下文：

```json
{
  "query": "PID 控制器中积分环节对稳态误差和超调的影响",
  "profile": "handout-authoring",
  "courseSlug": "automatic-control",
  "lessonSlug": "unit-3-time-domain",
  "knowledgeNodeIds": ["kn-pid", "kn-steady-state-error"],
  "capabilityTargetIds": ["cap-parameter-tuning"],
  "role": "teacher",
  "language": "zh-CN"
}
```

Query normalization 应做几件事：

1. 中文/英文术语扩展，例如“相角裕度 / phase margin”，“根轨迹 / root locus”，“稳态误差 / steady-state error”。
2. 公式符号扩展，例如 `Kp Ki Kd`、`G(s)`、`ζ`、`ω_n`、`PM`。
3. 图谱邻居扩展，例如从当前知识节点扩展到先修、后继、同章节点。
4. 场景约束注入，例如控灵问答必须 `student-visible`，讲义制作可读 `teacher-scoped`，路径规划必须考虑 `PlanningUnit` eligibility。

你们最近已经在 adaptive planner 里扩展了 graphContext 输入，并持久化 graph/resource/overlay/version basis，这说明 Source Pack 的 query 也应吃同一类 graphContext，而不是只吃纯文本 query。

### 阶段二：多路召回

为了“较高召回率”，不要只用一个向量 top-k。建议至少四路召回：

```text
1. lexical retrieval：BM25 / PostgreSQL full-text / SQLite FTS
2. dense retrieval：embedding 向量检索
3. graph retrieval：知识节点、能力目标、LearningGoal、课程章节邻接扩展
4. exact retrieval：公式、术语、标题、图号、页码、资源 ID、CitationTarget 精确匹配
```

对 Mathpix 转出来的教材 md，尤其要做 formula-aware retrieval。很多控制理论内容单靠自然语言 embedding 会漏掉，例如：

```text
1 / (Ts + 1)
K / (s(s+a))
ζ, ω_n, M_p, t_s
|G(jω)|, ∠G(jω)
```

公式要单独做 normalized LaTeX tokens、symbol tokens、plain text tokens，不能只把 LaTeX 当普通文本。

图片描述也不要简单混入正文。应作为独立 chunk：

```text
modality = image-description
anchor = figure / page / image object key
generatedBy = multimodal-model
sourceImageHash = ...
```

讲义制作可以参考图片描述；控灵回答如果引用图片，应该引用“图像/图号/页码/标题”，而不是引用“模型生成的图片描述”本身。

### 阶段三：融合排序

多路召回后建议用 RRF 或类似方法融合：

```text
finalCandidateScore =
  lexicalScore
  + denseScore
  + graphAlignmentScore
  + authorityScore
  + citationReadinessScore
  + profileSpecificScore
```

不同 profile 权重不一样。

| Profile             | 排序重点                                                    |
| ------------------- | ------------------------------------------------------- |
| `handout-authoring` | 权威教材/参考书优先，章节覆盖优先，图表/公式出处优先，多样性高                        |
| `konling-answer`    | 学生可见、短证据、强相关、可直接引用，少而精                                  |
| `path-planning`     | LearningGoal/知识节点/能力目标匹配，资源可用性、预计用时、难度、path eligibility |
| `lesson-design`     | BOPPPS 环节、前测/后测、案例、图表、任务设计素材                            |
| `assessment-item`   | 定义、典型误区、可检验知识点、标准答案依据                                   |

### 阶段四：重排与去重

高召回会带来重复。教科书和参考文献经常同一段概念反复出现。建议做两层去重：

1. 同源相邻 chunk 合并，例如同一教材同一节连续命中的段落。
2. 跨源语义去重，避免 pack 里 8 条都在说“积分环节消除稳态误差”。

Source Pack 应强制多样性，例如：

```text
最多 40% 来自同一本书；
至少覆盖 2 类 sourceKind；
若涉及公式，至少保留 1 条 equation modality；
若涉及图形解释，优先保留 figure/image-description；
若用于路径规划，必须标记哪些是 pathEligible，哪些只是 citation-only。
```

### 阶段五：Pack assembly

最后生成两个输出：

```text
source-pack.json   机器可读
source-pack.md     给 Codex/技能/人工作者读
```

`source-pack.md` 不要太长。建议格式：

```md
# Source Pack: 相角裕度与稳定性

## Query Context
- profile: handout-authoring
- course: 自动控制原理
- graph nodes: kn-frequency-response, kn-phase-margin
- index version: ...

## Coverage Summary
- 覆盖：相角裕度定义、Nyquist/Bode 关系、稳定裕度解释、工程调参意义
- 缺口：船舶航向控制案例证据不足

## Recommended Sources

### S1. 《自动控制原理》...
- CitationTarget: textbook:xxx#section-5-3-page-128
- Modality: text + equation
- Why included: 给出相角裕度定义与稳定性关系
- Excerpt: ...

### S2. ...
```

对于 Codex/技能来说，默认只读 `source-pack.md`。需要深入时再按 `citationTargetId` 调用：

```bash
npm run source-pack -- show --citation-target textbook:ogata#ch5-sec3-p128
```

这比一次性塞 50 个 chunk 进上下文更好。

## 4. 不要绕开现有资源治理

项目现在已经不是一个简单内容站。它有课程 runtime、知识图谱、资源注册、数据治理、控灵上下文、路径规划、学习事实、学生画像等多层结构。Source Pack 必须接入这些层，而不是只对 `*.md` 建索引。

建议源数据优先级：

```text
一级：已经治理后的 RetrievalChunk / CitationTarget / ResourceSegment
二级：runtime resource projection sidecar
三级：course-content/runtime 下的 lesson / media / knowledge card
四级：authoring 原始 md / Mathpix md / 图片描述
五级：外部链接，仅作为 fallback，不作为稳定 citation
```

这有两个好处：

第一，避免引用未审核、未版本化、无权限标记的原始材料。

第二，路径规划和控灵能共享同一批 citation target。否则讲义制作可能引用了一个教材图，但控灵不知道这个图属于哪个知识节点，也不知道能不能给学生看。

## 5. Mathpix 教材资源的索引策略

你这批资源价值很高，应该专门建一种 `TextbookReferenceAsset` 或等价资源类型。

建议 ingestion 时保留以下结构：

```text
Book
  ├─ Chapter
  │   ├─ Section
  │   │   ├─ ParagraphChunk
  │   │   ├─ EquationChunk
  │   │   ├─ FigureChunk
  │   │   ├─ TableChunk
  │   │   └─ ImageDescriptionChunk
```

每个 chunk 都要有：

```text
sourceBookId
edition / version
chapterTitle
sectionTitle
pageStart / pageEnd
headingPath
chunkText
normalizedText
latexTokens
figureRefs
tableRefs
imageObjectKey
sourceHash
visibility
license
citationTargetId
graphNodeRefs
```

特别要注意三点。

第一，**页码和章节路径必须保留**。讲义制作最需要“这个判断来自哪本书哪一节”，不是只需要语义片段。

第二，**图片描述要标记为生成内容**。图片描述很有用，但它不是原始教材文本。Source Pack 应显示：

```text
modality: image-description
provenance: generated_from_source_image
sourceImageHash: ...
descriptionModel: ...
```

第三，**公式要独立成 chunk**。控制理论讲义经常围绕公式组织。如果公式只混在自然段中，召回率和引用质量都会下降。

## 6. 本地 CLI 与服务器控灵的双模式

你提到“Codex 写讲义可以用，控灵在服务器上也可以用”。这两个环境不同。

Codex/技能侧适合：

```text
local mode
- 读取本地 index bundle
- 生成 source-pack 文件
- 返回 pack 路径和摘要
```

服务器控灵适合：

```text
service mode
- 调用同一 source-pack core
- 走数据库/向量库/缓存
- 严格按用户角色过滤
- 控制延迟和并发
```

不要让线上控灵每次问答都 `spawn CLI`。可行但不优雅，延迟、安全、并发控制都麻烦。更好的做法是：

```text
CLI = authoring / Codex / 运维工具
Node library 或内部 API = 控灵生产服务
```

同一个 CLI 可以支持两种后端：

```bash
npm run source-pack -- build \
  --backend local-index \
  --profile handout-authoring \
  --query "根轨迹的渐近线与分离点"

npm run source-pack -- build \
  --backend server \
  --profile konling-answer \
  --query "为什么积分环节会增加超调？" \
  --role student
```

## 7. Index bundle 设计

如果 Codex/技能要本地用，就不能完全依赖线上数据库。建议生成一个可缓存的本地索引包：

```text
.rag-index/
  index.manifest.json
  chunks.sqlite              # FTS5 + metadata
  vectors.bin / vectors.hnsw # 向量索引，可选
  resources.jsonl
  citation-targets.jsonl
  graph-bindings.jsonl
  embeddings.manifest.json
```

`index.manifest.json` 记录：

```json
{
  "indexVersion": "2026-06-xx",
  "builtAt": "...",
  "embeddingModel": "...",
  "chunkCount": 128000,
  "resourceCount": 4200,
  "citationTargetCount": 98000,
  "graphCatalogVersion": "...",
  "resourceProjectionVersion": "...",
  "sourceHashes": {}
}
```

CLI 每次生成 Source Pack 时，把 index version 写进去。这样以后讲义内容出了问题，可以回放当时检索依据。

大型向量索引不要直接进 Git。更合理的是：

```text
Git 里保存 index manifest + 小型元数据；
OSS 或服务器保存完整 index bundle；
本地 CLI 首次运行时下载缓存；
CI 或 Codex 环境没有向量索引时，退化到 FTS + graph + exact retrieval。
```

## 8. CLI 命令设计

建议命令分四组。

### 1. index

```bash
npm run source-pack -- index build \
  --input course-content/reference \
  --output .rag-index \
  --include-mathpix \
  --include-image-descriptions

npm run source-pack -- index status

npm run source-pack -- index doctor
```

`doctor` 用来检查：

```text
chunk 是否有 citationTargetId
图片描述是否有 sourceImageHash
公式 chunk 是否可检索
resourceNodeId 是否能回到 registry
student-visible 资源是否混入 teacher/admin scope
indexVersion 是否和 runtime projection version 对齐
```

### 2. search

```bash
npm run source-pack -- search \
  --query "相角裕度" \
  --profile handout-authoring \
  --top-k 50 \
  --explain
```

这个命令用于调试召回，不生成正式 pack。

### 3. build

```bash
npm run source-pack -- build \
  --query "PID 控制器中积分环节对系统性能的影响" \
  --profile handout-authoring \
  --course automatic-control \
  --lesson unit-3-pid \
  --top-k 160 \
  --pack-size 20 \
  --out .source-packs/pid-integral-effect
```

输出：

```text
.source-packs/pid-integral-effect/source-pack.json
.source-packs/pid-integral-effect/source-pack.md
.source-packs/pid-integral-effect/source-pack.audit.json
```

### 4. eval

```bash
npm run source-pack -- eval \
  --gold tests/fixtures/source-pack-gold.jsonl \
  --profile handout-authoring
```

评估指标：

```text
Recall@20：目标教材章节是否被召回
Citation accuracy：citationTarget 是否可回放
Authority coverage：权威来源占比
Duplicate rate：重复片段比例
Forbidden leakage：学生 profile 是否泄露 teacher/admin 资源
Modality coverage：公式/图/表是否被召回
```

## 9. 和讲义制作技能的集成方式

讲义制作技能不要直接读全部教材。技能流程应变成：

```text
1. 根据讲义主题生成检索请求
2. 调用 source-pack CLI
3. 读取 source-pack.md
4. 生成讲义大纲
5. 如某个知识点证据不足，再二次调用 CLI
6. 输出讲义时保留 source notes / citationTargetId
```

例如：

```bash
npm run source-pack -- build \
  --profile handout-authoring \
  --query "根轨迹法的基本规则、渐近线、分离点和稳定性判断" \
  --course automatic-control \
  --knowledge kn-root-locus \
  --pack-size 24 \
  --out course-content/authoring/lessons/unit-root-locus/source-packs/root-locus
```

技能读取：

```text
course-content/authoring/lessons/unit-root-locus/source-packs/root-locus/source-pack.md
```

不建议让技能直接把 pack 全部塞进最终讲义。正确做法是：

```text
source pack 负责提供依据；
讲义负责重新组织教学表达；
引用保留 citationTarget；
不要长段复制教材。
```

这点对版权和教学质量都重要。尤其教材和参考书资源，Source Pack 应该提供短摘录、页码、章节、图表锚点，而不是把原文大量输出给模型。

## 10. 和控灵的集成方式

控灵问答需要更严格：

```text
profile = konling-answer
role = student | teacher
maxPackItems = 6~10
maxExcerptChars = 1200~2000
mustHaveCitationTarget = true
mustRespectVisibility = true
```

控灵回答时流程：

```text
用户问题
  -> query normalization
  -> buildSourcePack(profile=konling-answer, role=currentUserRole)
  -> LLM answer with citations
  -> answer audit: 每个关键事实是否来自 pack item
  -> InteractionLog / LearningFact 可记录 packId
```

这样以后可以追踪：“控灵这次回答到底参考了哪些教材/讲义/图表”。

你们最近已经在做 Konling K/A/Q graph context，把 graph grounding 接入 runtime contracts、page-context tools 和 prompt construction。 Source Pack 应该成为这条链路的检索证据层，而不是另一个平行上下文。

## 11. 和路径规划的集成方式

路径规划不能直接消费“相关文本”。它需要资源候选。

因此 `path-planning` profile 的 Source Pack Item 应多几个字段：

```ts
pathPlanning?: {
  pathEligible: boolean;
  planningUnitId?: string;
  estimatedTimeMinutes?: number;
  difficulty?: "intro" | "core" | "advanced";
  prerequisites?: string[];
  targetKnowledgeNodes: string[];
  targetCapabilities: string[];
  reasonIfNotEligible?: string;
};
```

路径规划可以使用 pack，但必须遵守现有 eligibility：

```text
可进路径：PlanningUnit / pathEligible ResourceNode
可引用：CitationTarget / RetrievalChunk
可解释：Textbook/reference/image description
不可直接推给学生：teacher/admin scoped、未人审、缺版本、stale、citation-only
```

换句话说，Source Pack 不是直接替代 planner 的候选生成器，而是提供“可解释的资源证据包”。Planner 仍然必须按 LearningGoal、能力目标、路径约束、学生画像生成路径。

## 12. 权限和治理规则必须前置

这是最容易出事故的地方。

Source Pack Builder 必须先做权限过滤，再排序。不能先检索、再让 LLM 自己忽略不可见资源。

建议规则：

```text
student profile:
  只允许 student-visible
  禁止 admin-scoped / teacher-scoped
  禁止 aiUsePermission=blocked
  禁止 citationReadiness=false 的材料进入回答 pack

teacher / handout-authoring profile:
  可读 teacher-scoped
  admin-scoped 仍默认禁止，除非显式 --role admin
  未审核资源可作为 "candidate"，但不能作为 authoritative source

path-planning profile:
  必须区分 citation-only 和 pathEligible
```

尤其是你有大量由多模态模型生成的图片描述，这类内容应默认：

```text
可以作为检索增强线索；
不能单独作为权威事实来源；
引用时必须回到原图、图号、页码或教材位置。
```

## 13. 本地子代理和 Codex 的配合

你前面提到开发流程中 GitHub Codex 会发现本地子代理漏掉的 P1/P2。Source Pack 工具本身很容易踩类似问题，所以一开始就应把 failure mode 写进测试。

重点测试：

```text
空 query、超长 query、公式 query、英文 query、中英混合 query
不存在的 knowledgeNodeId
student profile 下 teacher-scoped 泄露
citationTargetId 缺失
image-description 没有 sourceImageHash
chunk 有 excerpt 但没有 source page/section
重复 chunk 过多
同一本书垄断 pack
path-planning profile 返回 citation-only 资源却标 pathEligible
indexVersion 与 resourceProjectionVersion 不一致
```

每次 Codex 对 Source Pack 提出问题，都应该沉淀到 `tests/fixtures/source-pack-failure-modes`。

## 14. 开发路线

我建议分四个 PR 做，不要一个 PR 做完整大系统。

**PR 1：Source Pack 协议和只读 CLI skeleton**

目标是不改现有 RAG，只包装已有检索结果。

交付：

```text
src/lib/source-pack/source-pack-types.ts
src/lib/source-pack/source-pack-builder.ts
scripts/source-pack/source-pack-cli.ts
tests for serialization / permissions / empty results
```

CLI 可以先 mock 或调用现有 hybrid retriever。

**PR 2：接入现有 RetrievalChunk / CitationTarget / ResourceSegment**

目标是让 pack item 全部带稳定 citation。

交付：

```text
citation hydrator
resource metadata join
visibility filtering
pack markdown renderer
```

**PR 3：profile-aware ranking**

目标是区分 handout、konling、path-planning。

交付：

```text
retrieval-profiles.ts
RRF fusion
MMR diversity
authority scoring
graph alignment scoring
```

**PR 4：index bundle 和 authoring skill 集成**

目标是让 Codex/技能能本地调用。

交付：

```text
.rag-index manifest
index doctor
source-pack build command
讲义制作 skill 调用规范
golden query eval
```

如果一开始就把本地索引、服务器检索、权限、图谱、讲义技能、控灵、路径规划全部做完，PR 会很大，Codex 会持续挖边界问题。这里应该刻意拆。

## 15. 最关键的设计取舍

我会明确建议：

**做 CLI，但不要让 CLI 成为系统真源。系统真源应该是 Source Pack Core + Resource/Citation 治理层。**

CLI 负责：

```text
本地调用
调试
Codex/技能集成
作者态 source pack 生成
批量评估
```

服务端负责：

```text
控灵在线检索
权限过滤
低延迟缓存
学习行为记录
source pack 审计
```

Source Pack 负责：

```text
统一格式
统一引用
统一权限
统一版本
统一覆盖度说明
```

MCP 可以以后再包一层，但不是第一优先级。当前你的判断是对的：CLI 更适合技能按需取用，尤其适合“生成 pack 文件，然后只把摘要读进上下文”的工作流。后面如果需要给 IDE、agent platform 或教师端提供交互式检索，再把同一个 `buildSourcePack()` 暴露成 MCP tool 或内部 API 即可。

最终要避免的是两种极端：

一是只做一个简单 CLI，把 md 检索结果吐给模型。这会很快变成不可审计、不可权限控制、不可复现的“高级 grep”。

二是直接把所有教材内容塞进 MCP/RAG 长上下文。这会让上下文污染严重，而且不能保证引用稳定。

更稳的方案是：**高召回检索在外部完成，Source Pack 做压缩、分层、去重、权限过滤和引用稳定化，智能体只消费经过治理的 pack。**


# Pro relay 2:

这个方向是合理的，而且比“把所有参考资料塞进技能上下文”更符合你当前项目的结构。我的判断是：应当做，但不要把它做成一个单纯的“搜索脚本”；更合理的是做成一个统一的“参考资源检索与 source pack 生成层”，CLI 只是其中一个入口。否则后续会出现三套口径：控灵一套 RAG，讲义制作一套 CLI，路径规划一套资源节点，最后引用 ID、证据粒度、召回策略都不一致。

基于我已经读取到的项目结构，你现在的平台有几个关键事实：课程内容采用 `course-content/authoring/` 到 `course-content/runtime/` 的作者态/运行态分层；正式页面通过 runtime 读取讲义、知识图谱、知识卡和媒体索引；AI 能力不是独立聊天入口，而是嵌入 `/api/ai/chat`、`/api/ai/konling-context`、课程级 `src/lib/course-ai-contexts.ts`、`src/lib/unit-*-ai-contexts.ts` 和仿真伴学链路；教学事件和学习画像又通过 `src/lib/data-governance/` 进入证据链。也就是说，你的资料检索工具不应只是“给 Codex 写讲义时临时查资料”，它应该成为课程内容生产、控灵回答、路径规划资源推荐和未来学习证据解释共同使用的参考资料层。

我建议把这个工具定位为：

“给定一个教学/科研/答疑/路径规划任务，基于教材、参考文献、课程 runtime、图片描述和已有知识节点进行高召回混合检索，经过去重、重排、证据裁剪和引用规范化，输出可被人类和智能体直接使用的 source pack。”

这里的核心产物不是检索结果列表，而是 source pack。source pack 应该是一个稳定格式的“证据包”，而不是一堆 chunk。它要解决三个问题：第一，保证召回；第二，降低上下文污染；第三，让下游生成内容可追溯、可复核、可引用。

我建议采用“三层架构”。

第一层是资源索引层，负责把 Mathpix 转换后的高精度 Markdown、图片描述、教材章节、参考论文、课程 runtime 讲义、知识卡片和知识图谱节点统一进入索引。这里不要直接以“文件路径 + chunk 文本”作为长期主键，应该有稳定的 `sourceId`、`sectionId`、`chunkId`。例如：

`sourceId = textbook-ogata-modern-control-5e`

`sectionId = ch04-root-locus-basic-rules`

`chunkId = textbook-ogata-modern-control-5e::ch04-root-locus-basic-rules::chunk-0007`

图片描述也应作为一等资料进入索引，而不是附属文本。Mathpix 文档里的图片描述可以建成 `modality=image-description` 的 chunk，并保留 `figureId`、`caption`、`page`、`nearbyText`、`imagePath`。这样讲义制作时可以检索到图像证据；控灵回答时可以引用“图示说明”；路径规划时可以推荐“包含关键图示的参考资源”。

第二层是检索服务层，负责混合检索、重排和 pack 组装。这个层应该做成普通 TypeScript library，例如放在 `src/lib/reference-retrieval/` 或沿用你现有 RAG 模块所在目录。CLI、API route、技能、控灵都调用这个 library。不要把主要逻辑写进 `scripts/xxx.ts`，否则服务器上的控灵无法干净复用，后续也难以测试。

第三层是入口层，包括 CLI、API、技能封装和控灵工具调用。CLI 是给 Codex、技能、本地批处理和课程制作使用的；API 是给线上控灵和平台页面使用的；技能只是读取 CLI 输出，而不是自己重写检索逻辑。

更具体地，我建议目录大致这样设计，具体命名可以和你现有 RAG 目录对齐：

```text
src/lib/reference-retrieval/
  index.ts
  types.ts
  query-normalizer.ts
  hybrid-search.ts
  rerank.ts
  source-pack.ts
  citation.ts
  filters.ts
  token-budget.ts
  adapters/
    textbook-markdown.ts
    course-runtime.ts
    knowledge-card.ts
    paper-markdown.ts
    image-description.ts

scripts/reference/
  build-index.ts
  retrieve-source-pack.ts
  inspect-source.ts
  eval-retrieval.ts

docs/reference-retrieval/
  source-pack-schema.md
  retrieval-policy.md
  evaluation.md
```

如果你现有基本 RAG 已经有目录，例如 `src/lib/rag/`、`src/features/ai/rag/` 或类似结构，那就不要另建平行系统，而是在现有实现外面增加 `source-pack` 这一层。关键是保证“线上控灵”和“离线讲义制作”使用同一套 chunk ID、metadata、引用格式和排序策略。

CLI 的目标不应只是“搜索”，而应支持几类任务模式。不同模式的召回策略不同。

第一类是讲义制作模式。它需要高召回、高权威、低噪声。查询通常是一个课时、一个知识点或一段设计 brief，例如“根轨迹法的幅值条件与相角条件讲义”。它应该优先召回教材、课程 runtime、权威参考文献、图示说明和已有知识卡片。输出应包含“可直接引用的定义、公式、推导、例题、图示建议、易错点”。这类 pack 可以较长，适合 Codex 写讲义前读取。

第二类是控灵答疑模式。它需要低延迟、强引用、答案支撑性。查询通常是学生问题和当前课堂上下文。它不需要返回太多材料，应该返回紧凑 pack，并且每条证据都要有明确引用路径。控灵不应拿到 30 个 chunk，而应拿到 5–8 条高置信证据、2–3 条补充证据和必要的“不要越界回答”的提示。

第三类是学习路径规划模式。它关心资源节点、先修关系、难度、知识点覆盖和学习任务适配。检索结果不只是文本证据，还应包含资源类型、适合对象、难度、预计学习时间、关联知识节点、是否包含例题/图示/仿真/练习。这里 source pack 应该更像“候选资源包”，供路径规划器做排序和组合。

第四类是科研/参考文献模式。它需要论文、综述、公式来源、方法对比、实验设置。此时检索策略要提高 reference/paper 权重，并在 pack 中明确“教材性资料”和“研究性资料”的角色差异。

CLI 可以这样设计：

```bash
npm run source:pack -- \
  --query "根轨迹法的幅值条件和相角条件如何用于自动控制原理讲义" \
  --mode lecture \
  --course automatic-control \
  --lesson 4-2 \
  --nodes root-locus,characteristic-equation \
  --top-k 40 \
  --pack-size medium \
  --format markdown \
  --out .tmp/source-packs/unit-4-2-root-locus.md
```

控灵或服务器使用可以是：

```bash
npm run source:pack -- \
  --query "为什么闭环极点越靠左响应越快" \
  --mode konling \
  --student-level undergraduate \
  --lesson 3-1 \
  --format json
```

路径规划可以是：

```bash
npm run source:pack -- \
  --query "学生时域分析薄弱，需要推荐学习阻尼比、超调量、调节时间" \
  --mode path-planning \
  --profile student-competency \
  --nodes damping-ratio,overshoot,settling-time \
  --format json
```

参数上，我建议至少支持：

`--query`：自然语言查询。

`--mode`：`lecture | konling | path-planning | research | general`。

`--course`、`--lesson`、`--nodes`：课程上下文过滤或加权。

`--source-types`：`textbook,paper,runtime-handout,knowledge-card,image-description`。

`--authority`：权威级别过滤，例如 `core-textbook,reference,paper,course-authored`。

`--recall`：`high | balanced | precise`。

`--pack-size`：`small | medium | large`，控制 token budget。

`--format`：`markdown | json | jsonl`。

`--out`：输出路径。

`--explain`：输出检索解释，包括关键词匹配、向量相似度、重排得分、过滤条件。

`--include-images`：是否纳入图片描述证据。

`--dedupe`：按 source/section/semantic 去重。

`--max-per-source`：防止一个教材章节垄断 pack。

`--fail-on-low-confidence`：低置信时退出非零状态，避免技能误用低质量资料。

混合检索本身，我建议采用“召回宽、组包严”的策略。你希望它用于讲义制作，宁可召回阶段多拿一些，再在 source pack 阶段压缩。检索可以分四路：

一是关键词检索。对公式、术语、章节号、定理名、英文缩写非常重要。比如 “Routh-Hurwitz”“Nyquist”“相角裕度”“damping ratio” 这类内容，纯向量检索不够可靠。关键词检索还应支持中英文同义词。

二是向量检索。用于语义相近但表述不同的内容，例如“动态性能指标”和“瞬态响应评价”。

三是结构化过滤。按课程、章节、知识节点、资源类型、教材版本、页码、作者、年份、权威级别过滤或加权。

四是图谱扩展。既然项目已有知识图谱和知识卡，查询某个节点时可以自动扩展先修、后继和同层关联节点。例如检索“根轨迹渐近线”时，同时轻度扩展“闭环特征方程”“极点零点”“稳定性”“根轨迹绘制规则”，但扩展权重要低，避免跑偏。

重排阶段不要只用一个综合分。建议分成几个分量：

`semanticScore`

`keywordScore`

`authorityScore`

`courseContextScore`

`nodeCoverageScore`

`freshnessScore`，对教材一般不重要，对论文重要

`modalityBonus`，例如图片描述对讲义制作有加成

`diversityPenalty`，防止同一来源重复

最终 source pack 不应按原始分数简单排列。讲义制作时更好的组织方式是：

“核心教材证据”

“公式与定义”

“推导与方法”

“例题/应用场景”

“图示与可视化材料”

“易错点与边界条件”

“可引用参考文献”

控灵答疑时则应组织为：

“直接回答证据”

“补充解释证据”

“当前课堂上下文”

“引用清单”

“低置信或冲突提示”

路径规划时应组织为：

“候选资源节点”

“覆盖知识点”

“适用学习目标”

“推荐理由”

“先修要求”

“可配套练习/仿真”

这里有一个必须提前定下来的原则：source pack 中最好不要大量放原文长摘录。尤其是教材和参考书，即使你本地有转换后的 Markdown，也应尽量以“短摘录 + 摘要 + 定位引用”为主。讲义制作时需要权威性，不意味着要复制教材段落。可以保留公式、定义的必要短文本，但正文应由课程作者重新组织。这样既降低版权风险，也能避免讲义变成参考书拼贴。

你提到图片也已经用多模态模型给了描述并嵌入文档，这部分很有价值，但需要结构化处理。建议在索引时把图片描述拆成三类字段：

`visualSummary`：图像整体描述。

`pedagogicalUse`：这张图适合说明什么概念。

`technicalDetails`：坐标轴、变量、曲线、框图关系、公式标注等。

例如一张根轨迹图，普通描述可能说“图中有若干曲线从开环极点出发趋向开环零点”。但教学使用需要知道：它是否显示实轴段、渐近线、分离点、虚轴交点、参数变化方向。这些信息应进入 `technicalDetails`，否则图片检索命中后仍难以支撑讲义设计。

对 Mathpix 文档的 chunking，我建议不要使用固定长度切块作为主策略。教材和论文最重要的是结构。更好的切分顺序是：

先按 Markdown 标题层级切分章节、节、小节；

再按公式块、定义、定理、例题、图表说明形成语义单元；

过长语义单元再滑窗切分；

chunk metadata 保留 heading path，例如 `第4章 > 根轨迹法 > 根轨迹条件`；

公式块要和前后解释绑定，避免检索出一个孤立公式。

对于自动控制原理教材，公式附近上下文特别重要。检索 `ζ` 或 `超调量` 时，如果 chunk 只包含公式，没有“二阶系统欠阻尼阶跃响应”的上下文，下游生成就容易误用。因此建议 chunk 至少包含：

前导解释

公式 LaTeX

变量定义

适用条件

紧邻例子或图示引用

这也意味着索引阶段要做一个“formula-aware chunker”。Mathpix 的 Markdown 本身保留公式结构，正好可以利用。

权威性分层也要做。否则高召回会把很多弱材料召回来。建议给每个 source 定义：

`authorityLevel`

`sourceType`

`courseRelevance`

`licenseStatus`

`language`

`edition`

`domain`

例如：

核心教材：`authorityLevel=5`

权威参考书：`authorityLevel=4`

课程自建讲义/runtime：`authorityLevel=4`

高质量综述/经典论文：`authorityLevel=4`

普通论文：`authorityLevel=3`

网页/非正式材料：如果未来加入，默认不超过 2

控灵答疑默认应优先 `authorityLevel >= 4`。讲义制作可以使用 `>=3`，但核心定义和公式应来自高权威来源。

为了保证高召回，我建议建立查询扩展机制，但要受控。比如“路径规划”可能涉及 learning path planning、personalized learning path、curriculum sequencing、knowledge tracing、mastery learning、recommendation、prerequisite graph；“根轨迹”涉及 root locus、closed-loop pole、characteristic equation、angle criterion、magnitude criterion。查询扩展来源应包括：

课程知识图谱节点别名；

中英文术语表；

教材索引词；

用户提供的 lesson/node 上下文；

最近课堂或讲义上下文。

但扩展词不能无脑加入最终 query。应区分：

`mustTerms`：必须匹配或强加权；

`shouldTerms`：提高召回；

`negativeTerms`：排除容易混淆方向；

`contextTerms`：只作为重排加权。

例如讲义模式下检索“频域稳定裕度”，可以扩展到 phase margin、gain margin、Bode、Nyquist，但如果当前 lesson 是 Bode 图，就应降低 Nyquist 的扩展权重，避免把另一个章节的材料召回过多。

我建议 source pack 生成时做“证据预算”，而不是简单 top-k。比如 medium pack 预算 12,000 tokens，可以这样分配：

核心定义与公式：30%

教材解释：25%

课程已有 runtime/知识卡：15%

图示与媒体描述：10%

例题与应用：10%

补充论文/参考：10%

这样可以避免一个大 chunk 把上下文占满。对于控灵 small pack，可能只有 2,000–4,000 tokens，应只返回直接证据和引用定位。

和你现有技能体系结合时，我建议每个相关技能只知道“如何调用 CLI”和“如何消费 pack”，不要把检索策略复制到技能说明里。比如：

`lesson` 技能：在生成讲义前调用 `source:pack --mode lecture`，把 pack 作为证据，不直接改写教材原文。

`interactive-design` 技能：调用 `source:pack --mode lecture --include-images`，优先使用图示、例题、误区证据设计互动步骤。

`lesson-content-review` 技能：调用 `source:pack --mode review` 或 `lecture`，对 handout 中的事实、公式和术语做核对。

`refine` 技能：默认不需要调用，除非润色中涉及事实改写。

`infograph` 技能：调用 `source:pack --mode visual`，取图示描述、公式结构和教学用途。

`openspec-propose/apply`：涉及检索工具本身开发时读取相关设计文档。

可以在 `.agents/skills/README.md` 中新增一节“参考资料检索工具”，但不要让所有任务默认调用。默认调用会拖慢流程，也会污染上下文。原则是：只在生成知识密集型内容、核对事实、设计学习路径、控灵需要引用时调用。

服务器上的控灵使用时，要注意 CLI 不应成为高并发路径的性能瓶颈。线上场景最好不是每次 fork 一个 Node/tsx 进程做检索，而是复用同一套 library，由 API route 或服务端函数直接调用。CLI 适合本地 Codex、脚本和低频批处理。也就是说：

本地/技能：CLI。

线上控灵：library 或 API。

调试/审计：CLI + `--explain`。

如果一定要让控灵也调用 CLI，至少要有缓存和超时控制。比如相同 `query + context + mode + filters` 生成 `cacheKey`，短期缓存 source pack；CLI 默认超时 8–15 秒；低置信时返回结构化错误，而不是让控灵编造引用。

评估体系也必须同时做。否则“高召回”会停留在主观感受。建议先建立一个小型 gold set。每个课程模块选 5–10 个典型查询：

定义类：什么是相角裕度？

公式类：二阶系统超调量公式如何推导？

图示类：根轨迹渐近线怎么画？

例题类：如何从 Bode 图判断稳定裕度？

路径规划类：学生不理解阻尼比，应推荐哪些资源？

讲义制作类：为“Nyquist 稳定判据”准备资料包。

每个查询标注应命中的教材章节、知识卡、公式、图片或论文。然后评估：

Recall@20

MRR

nDCG

source diversity

citation correctness

pack usefulness，人评即可

hallucination resistance，也就是 pack 是否包含足够边界条件

CLI 应提供：

```bash
npm run source:eval
```

输出每次改索引或改排序后的指标变化。没有这个，很容易调着调着把控灵答疑做准了，却把讲义召回做窄了。

还有一个重要问题：动态 source pack 会不会导致讲义制作不可复现？如果今天检索一次、明天索引更新后再检索一次，生成的讲义依据可能不同。建议每个 pack 保存：

`packId`

`indexVersion`

`retrievalPolicyVersion`

`sourceSnapshot`

`query`

`filters`

`generatedAt`

课程作者态中可以把最终使用过的 pack 存档到 lesson notes 或 `.tmp/source-packs/`，重要讲义甚至应记录在 `course-content/authoring/lessons/<lesson>/references/`。这样以后审查时知道某段讲义依据什么资料生成。

我对 MVP 的建议是分四步，不要一次性做成大系统。

第一步，定义 schema 和最小 CLI。复用现有 RAG 索引，只做 `retrieve-source-pack.ts`，支持 `--query --mode --format --out --top-k --pack-size --explain`。输出 Markdown 和 JSON。先服务讲义制作。

第二步，补 metadata 和 source pack 组装。把教材、论文、图片描述、课程 runtime、知识卡片统一成 source item。加入去重、按来源限额、引用格式。此时开始让 `lesson`、`interactive-design`、`lesson-content-review` 技能使用。

第三步，加入查询扩展和图谱上下文。接入知识节点、lesson id、course runtime，使检索能够围绕具体课程目标而不是泛泛搜索。

第四步，线上控灵复用。把 CLI 背后的 library 接入 `/api/ai/konling-context` 或现有 RAG 服务，保证控灵引用和离线讲义引用同源。再加缓存、超时、低置信处理。

如果从文件和接口命名上更贴合你的平台，我会建议 npm scripts 叫得直白一点：

```json
{
  "scripts": {
    "source:pack": "tsx scripts/reference/retrieve-source-pack.ts",
    "source:index": "tsx scripts/reference/build-index.ts",
    "source:inspect": "tsx scripts/reference/inspect-source.ts",
    "source:eval": "tsx scripts/reference/eval-retrieval.ts"
  }
}
```

source pack 的默认输出目录：

```text
.tmp/source-packs/
```

正式沉淀的课程证据包：

```text
course-content/authoring/lessons/<lesson>/references/source-packs/
```

检索策略文档：

```text
docs/reference-retrieval/retrieval-policy.md
```

如果这个能力会长期作为课程生产基础设施，我建议走 OpenSpec。这个变更跨越 AI、课程作者态、控灵、技能和可能的服务器运行时，不应直接凭感觉开写。OpenSpec 的 proposal 应明确三条边界：

它不替代现有 RAG，而是复用并增强 source pack 组装。

它不把教材全文塞给模型，而是输出可追溯、预算受控的证据包。

它同时服务离线创作和在线控灵，但线上入口不依赖 CLI 进程。

我会反对的一种实现方式是：直接写一个 `scripts/search-rag.ts`，把向量检索和关键词检索拼一下，然后让技能读取输出。这种做法短期快，但会留下几个问题：无法保证引用口径统一；source pack 没有稳定 schema；控灵复用困难；路径规划拿不到资源节点 metadata；讲义审查无法复现；后续每个技能会发展出自己的检索参数，系统重新碎片化。

更合理的设计是：统一 retrieval core，多个入口；统一 source schema，多种 pack profile；统一 citation ID，多种消费方式。

我的最终建议是：做 CLI，而且应该尽快做。但把 CLI 视为“项目参考资料层的命令行入口”，不要把它视为“给 Codex 查资料的小工具”。它最有价值的地方不是方便检索，而是把你新积累的 Mathpix 教材、图片描述、参考文献、课程 runtime 和知识图谱，变成一个可复用、可追溯、可评估、可被不同智能体共同调用的证据基础设施。
