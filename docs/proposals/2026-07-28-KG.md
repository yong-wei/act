# ACT 对 ActKG 标准公开发布包的兼容与导入说明

文档标识：

```text
act-actkg-public-bundle-compatibility-v1
```

适用上游合同：

```text
ActKG Public Bundle Contract: actkg-public-bundle/1
CTKG Schema: 0.2.0
```

适用发布类型：

```text
module
integration
aggregate
```

ACT 正式候选知识底座只接收：

```text
bundle_kind=aggregate
release_stage=stable
```

模块包和 Integration 包作为组件谱系验证对象，不得作为与聚合包并列的当前 ReleaseSet 成员重复导入。

---

## 一、目的与范围

本说明用于使 ACT 能够识别、验证、导入和增量接收今后按照 `actkg-public-bundle/1` 规范发布的知识图谱包。

本次兼容建设只调整：

```text
公开包发现
Bundle合同识别
Artifact角色解析
组件谱系验证
导入收据
版本差异计算
候选ReleaseSet装载
```

不修改：

```text
AuthoritativeKnowledgeRepository 的运行时权威边界
现有知识图谱查询 API
节点和关系 DTO
候选、活动、Legacy 三类 selector
图谱画布
节点详情接口
控灵知识查询接口
正式生产切换机制
```

ACT 现有规范已经要求所有运行消费者只通过 `AuthoritativeKnowledgeRepository` 读取已验证的数据库数据，Repository 不得直接读取 Release 文件，也不得在候选不可用时回退到文件或 Legacy 数据。该边界继续保持。

---

# 二、当前实现的定位

现有 #1125 实现应保留为：

```text
CTKG 0.2 / control-theory-engineering-v0.2
历史精确适配器
```

它不能继续承担未来通用发布协议。

当前适配器在代码中明确声明：

* 只接收锁定的 `control-theory-engineering-v0.2`；
* 不声称兼容其他发布版本或其他 Schema；
* 固定 ReleaseSet ID、Release ID、上游提交和 Schema 哈希；
* 固定读取单一 Projection 文件。

当前锁定验证还要求 ReleaseSet 只有一个固定成员，并对具体 v0.2 Release 身份执行精确比较。

因此，新兼容层应采用：

```text
Public Bundle Router
├── actkg-public-bundle/1
│   └── ManifestDrivenBundleAdapter
└── 无bundle-manifest.json
    └── LegacyExactV02Adapter
```

规则如下：

1. 存在 `bundle-manifest.json` 时，只能走标准 Bundle 适配器。
2. 不存在 Manifest 时，只允许命中已经冻结的 v0.2 历史精确适配器。
3. 不得在标准包验证失败后退回旧适配器。
4. 不得通过目录扫描、“最新版”命名或最大版本号自动选择包。
5. #1125 已导入的数据、收据和历史适配代码不得改写。

# 三、版本身份必须分层

ACT 必须区分以下四种身份。

| 身份                                 | 含义             | 主要用途                    |
| ---------------------------------- | -------------- | ----------------------- |
| `bundle_id`                        | 一次公开包装修订       | 原始文件、Manifest和导入收据      |
| `release_id` / `release_hash`      | 一次知识语义发布       | 规范对象和关系的版本身份            |
| `release_set_id`                   | ACT 接受和选择的候选集合 | Repository、缓存和 selector |
| `projection_id` / `version_digest` | 一个公开投影视图       | 画布、详情和审计视图              |

例如：

```text
bundle_id:
  ctb:control-theory-engineering-v0.4:r1

release_id:
  ctr:release:control-theory-engineering-v0.4

release_set_id:
  actkg-authoritative-candidate-v4

projection_id:
  ctr:projection:control-theory-engineering-v0.4:runtime
```

不得把 `bundle_id` 当作图谱语义版本，也不得用目录名代替 `release_id`。

# 四、ACT 兼容注册表

ACT 应建立独立的机器可读兼容注册表，例如：

```text
scripts/actkg-release/compatibility-registry.ts
```

注册表至少包含：

```yaml
bundle_contracts:
  actkg-public-bundle/1:
    supported: true
    manifest_validator: PublicBundleManifestV1

schema_contracts:
  "0.2.0":
    allowed_sha256:
      - "<经审核的CTKG 0.2.0 Schema哈希>"

artifact_contracts:
  ctkg-release/0.2:
    supported: true
  ctkg-graph-projection/0.2:
    supported: true
  actkg-projection-link-metadata/1:
    supported: true
  actkg-rag-crosswalk/1:
    supported: true
  actkg-component-manifest/1:
    supported: true
  actkg-provenance-stubs/1:
    supported: true
  actkg-validation-report/1:
    supported: true
  actkg-release-diff/1:
    supported: true
```

兼容判断必须同时使用：

```text
contract version
+
Schema version
+
Schema原始字节SHA-256
```

不能只比较 `schema_version=0.2.0`。同一版本号对应未知 Schema 哈希时，应失败关闭并进入兼容评审。

# 五、ACT ReleaseSet Lock v3

现有 `release-set.lock.json` 继续作为 ACT 明确审核和接收某个上游包的本地准入凭据，但不再复制全部文件列表、组件数量和数据计数。

建议升级为：

```text
actkg-release-set-lock/v3
```

示例：

```json
{
  "lock_version": "actkg-release-set-lock/v3",
  "release_set_id": "actkg-authoritative-candidate-v4",

  "bundle": {
    "controlled_path": "course-content/authoring/knowledge/releases/control-theory-engineering-v0.4",
    "bundle_id": "ctb:control-theory-engineering-v0.4:r1",
    "bundle_revision": 1,
    "bundle_digest": "...",
    "manifest_raw_sha256": "..."
  },

  "release": {
    "release_id": "ctr:release:control-theory-engineering-v0.4",
    "release_version": "control-theory-engineering-v0.4",
    "release_hash": "...",
    "source_dataset_hash": "..."
  },

  "compatibility": {
    "bundle_contract_version": "actkg-public-bundle/1",
    "schema_version": "0.2.0",
    "schema_sha256": "..."
  },

  "source_revision": {
    "commit": "<40位SHA>",
    "tag": "<稳定标签>"
  }
}
```

Lock 只固定：

```text
经过审核的Bundle身份
Manifest原始哈希
语义Release身份
Schema身份
受控目录
上游提交和标签
```

Artifact、组件和统计信息由 `bundle-manifest.json` 声明，由 ACT 重新验证，不在 Lock 中重复维护。

# 六、Bundle 发现与基本准入

ACT 标准导入入口接收一个明确的受控目录，不执行递归目录发现。

准入顺序：

```text
1. 读取ACT ReleaseSet Lock
2. 定位受控目录
3. 读取bundle-manifest.json原始字节
4. 验证Manifest raw SHA-256
5. 验证bundle_contract_version
6. 验证bundle_digest
7. 验证release_stage
8. 验证Schema身份
9. 按Artifact role发现文件
10. 验证组件闭包
11. 验证跨文件语义闭包
12. 事务导入
```

标准生产候选导入要求：

```text
bundle_kind = aggregate
release_stage = stable
```

`candidate` 包只允许通过显式的开发或影子命令读取，例如：

```text
--allow-candidate-bundle
```

它不得：

```text
进入部署脚本默认路径
移动候选selector
覆盖stable收据
参与正式切换
```

# 七、Artifact 必须按 Role 识别

ACT 不得再依据文件名拼接规则查找文件。

当前适配器固定读取：

```text
${release_version}.projection.json
${release_version}.rag-crosswalk.jsonl
```

并要求 Crosswalk 每行恰好具有三个字段。

标准适配器必须改为：

```text
bundle-manifest.artifacts
→ role
→ profile
→ contract_version
→ path
```

## 7.1 Aggregate Bundle 必需角色

| Role                       | Profile             | ACT处理                       |
| -------------------------- | ------------------- | --------------------------- |
| `release`                  | —                   | Schema验证并导入Release envelope |
| `ctkg_schema`              | —                   | 验证Schema版本和哈希               |
| `projection`               | `runtime`           | 导入候选Repository              |
| `projection`               | `domain`            | 原样保存并验证                     |
| `projection`               | `review`            | 原样保存并验证                     |
| `projection_link_metadata` | `runtime`或共享Profile | 关系治理信息导入                    |
| `rag_crosswalk`            | —                   | 原样保存并导入上游三元组                |
| `component_manifest`       | —                   | 组件身份闭合                      |
| `provenance_stubs`         | —                   | 保存公开来源定位                    |
| `validation_report`        | —                   | 独立复核后保存                     |
| `release_diff`             | —                   | 与ACT重算差异核对                  |
| `release_notes`            | —                   | 原始字节保存                      |

保留文件：

```text
bundle-manifest.json
SHA256SUMS
```

不需要作为 `artifacts` 数组成员，但 `SHA256SUMS` 必须覆盖 Manifest 和全部 Artifact。

## 7.2 未识别 Artifact

```text
未知required role
    → 拒绝整个Bundle

未知optional role
    → 校验哈希后原样保存
    → 不参与运行态投影

已知role但未知required contract_version
    → 拒绝整个Bundle

已知role但未知optional contract_version
    → 原样保存，不解析
```

# 八、Projection Profile 到 ACT 的映射

上游 Profile 与 ACT 内部 Projection 不是同一命名空间。

标准映射为：

```text
上游 runtime projection
    → ACT act.canvas.v2
    → ACT act.node-detail.v2 的基础对象和关系

上游 domain projection
    → 审计保存
    → 后续领域分析或RAG扩展候选

上游 review projection
    → ACT act.migration-review.v1
```

ACT 现有 Repository 已定义：

```text
act.canvas.v2
act.node-detail.v2
act.migration-review.v1
```

并要求这些视图绑定 ReleaseSet、Release Hash、Dataset Hash 和 Projection Digest。

## 8.1 对既有 `act` Profile 的过渡兼容

此前 v0.3 已经输出：

```text
act
domain
review
```

未来规范使用：

```text
runtime
domain
review
```

标准适配器可以提供一次受控别名：

```yaml
profile_aliases:
  runtime: act
```

只有 Manifest 明确声明别名，或兼容注册表为特定 Bundle 修订登记别名时，ACT 才能将 `act` 作为 `runtime` 使用。

不得通过以下方式猜测：

```text
文件名包含act
三个投影内容相同
投影数组中的第一个文件
```

# 九、多 Projection 不得合并推断

ACT 必须分别保存三个 Projection 的：

```text
projection_id
projection_profile
version_digest
raw artifact hash
node count
link count
```

即使当前三个文件的节点和关系完全相同，也不得：

```text
只保存一个Projection
复制一个Projection生成另外两个
认为三个digest可以相同
假设它们未来具有相同成员集合
```

运行态只导入 `runtime` Profile。

`domain` 和 `review` 可只保存原始字节、结构化摘要及验证结果，不要求立即建立独立运行表。

# 十、Projection Link Metadata 闭合

M1E 桥接发布已经使用 `projection-link-metadata.jsonl` 保存每条关系的 Tier、证据引用、组件归属和 Integration Release 谱系，从而避免消费者根据图边反推治理信息。

对于 ACT 运行投影，必须满足：

[
\text{runtime projection relation IDs}
======================================

\text{runtime link metadata relation IDs}
]

硬性检查：

```text
relation_id唯一
每条runtime关系恰好对应一行Metadata
Metadata中不存在runtime之外的孤儿关系
release_tier与ReleaseEntry一致
evidence_refs可解析到公开证据标识
review_decision_refs可解析
component_release_ids全部存在
integration_release_id存在或显式为空
```

若一个 Metadata 文件声明同时适用于：

```text
runtime
domain
review
```

ACT 必须先验证三个 Projection 的关系集合完全一致。

只要任一关系集合不同，就必须要求 Profile 专属 Metadata 文件。

导入后：

```text
关系谓词、方向和端点
    → 现有规范关系表

Tier、Evidence、组件和Integration谱系
    → 现有关系治理元数据或等价JSON envelope
```

无需修改图谱查询 API。

# 十一、组件解析与验证

每个组件必须具有完整身份：

```json
{
  "release_id": "...",
  "release_version": "...",
  "release_hash": "...",
  "release_contract_version": "ctkg-release/0.2",
  "component_role": "module",
  "dataset_identity": {
    "kind": "native",
    "schema_version": "0.2.0",
    "source_dataset_hash": "..."
  },
  "bundle_reference": {
    "bundle_id": "...",
    "bundle_revision": 1,
    "bundle_digest": "...",
    "manifest_sha256": "..."
  }
}
```

不得通过以下信息推断 `release_id`：

```text
release_version
目录名
文件名前缀
组件顺序
模块名称
```

当前 v0.3 的组件文件中，根轨迹和系统建模组件缺少 `release_id`，只有 Integration 组件具有完整ID。 发布器产生该问题的原因是直接复用了两个 provenance 对象，只为 Integration 组件显式填写了ID。

标准导入器对此必须失败关闭，不得补猜。

## 11.1 三处组件集合一致

以下三处的 `release_id` 集合必须完全一致：

```text
Aggregate Release.component_releases
bundle-manifest.components
component-releases.json
```

## 11.2 组件包解析

ACT ReleaseSet Lock 应提供组件 Bundle 的受控路径注册表，或由组件 `bundle_reference` 唯一定位已经 vendored 的组件 Manifest。

验证内容：

```text
组件bundle manifest原始哈希
组件bundle digest
组件release_id
组件release_version
组件release_hash
组件Schema身份
组件bundle kind
```

组件不得作为第二个当前 ReleaseSet 成员导入。当前 ACT 规范已经要求组件只作为聚合Release的不可变谱系，不得形成重复当前成员。

## 11.3 Dataset Hash 不应错误等同

组件：

```text
source_dataset_hash
```

绑定组件自己的私有 Dataset。

聚合：

```text
source_dataset_hash
```

绑定聚合 Dataset。

ACT 不得再要求：

```text
component.source_dataset_hash
=
aggregate.source_dataset_hash
```

两者独立验证，通过组件 Release Hash 和 Bundle 引用形成聚合谱系。

# 十二、Release 和成员闭合

ACT 应继续验证：

```text
Release.entries
Release.included_entities
Projection nodes
Projection links
Crosswalk published_entity_id
```

具体规则：

1. `entries.entity`唯一；
2. `included_entities`唯一；
3. 两者集合完全一致；
4. 每个投影节点的`entity_id`属于Release成员；
5. 每个投影关系的`relation_id`属于Release关系成员；
6. 关系两端节点均在同一运行Projection；
7. `release_tier`与ReleaseEntry一致；
8. `source_release`和`source_release_hash`与当前聚合Release一致；
9. `source_dataset_hash`与当前聚合Release一致；
10. 未发布或未决对象不得通过Projection绕过Release成员准入。

现有导入规范已经把 Release Entries、Included Entities、投影端点和来源Release身份的一致性作为整包原子准入条件，该原则保持不变。

# 十三、对象和关系语义兼容

## 13.1 对象类型

只要对象类型：

```text
属于已注册CTKG Schema
通过Projection Schema
```

ACT 就应无损保存。

当前支持：

```text
DomainConcept
Formula
KnowledgeStatement
SystemModel
ModelRepresentation
```

不支持专用业务行为的类型仍可进入：

```text
generic read-only projection
```

但不得参与尚未声明支持的业务计算。ACT Repository 当前已经规定：存储支持和消费者语义支持必须分离，合法但无专用适配器的类型可以只读呈现，并从不支持的业务计算中排除。

## 13.2 关系谓词

关系必须同时满足：

```text
谓词属于当前注册Schema
relation_family合法
direction合法
端点存在
端点类型签名合法
```

新关系只进入工程知识关系层，不自动进入：

```text
教学先修
课程包含
KAQ
学习路径
资源教学角色
学习事实
```

Gold/Silver原样保存：

```text
Gold
    → ACT核心候选集合

Gold + Silver
    → ACT扩展候选集合
```

但是否进入某门课程的正式使用范围，仍由 ACT CourseCoverage Overlay 决定。

# 十四、RAG Crosswalk

`actkg-rag-crosswalk/1` 每行严格包含：

```json
{
  "published_entity_id": "...",
  "retrieval_chunk_id": "...",
  "citation_target_id": "..."
}
```

ACT 导入阶段只验证：

```text
三字段存在且非空
无额外字段
三元组唯一
published_entity_id属于Release
记录数与Manifest一致
```

`retrieval_chunk_id` 和 `citation_target_id`继续作为上游不透明标识保存，不要求在知识包内部解析为 ACT 结构单元。现有正式规范也明确将其解析延期至课程和资源治理阶段。

不得在导入阶段：

```text
按字符串猜测教材单元
把Crosswalk当成教材正文
把图谱节点当作引用内容
自动生成资源教学角色
```

# 十五、原始字节与私有边界

ACT 必须保存公开 Bundle 中每个文件的：

```text
相对路径
role
profile
contract_version
required
media_type
raw SHA-256
byte_length
record_count
原始字节
```

现有规范要求公开Bundle全部原始字节可重建，并禁止从公开Projection或Crosswalk虚构私有CTKGDataset。

ACT 不得声称持有：

```text
SourceFragment.raw_text
EvidenceLink.exact_quote
完整教材正文
私有CTKGDataset
模型完整响应
私有审核草稿
```

除非未来公开 Bundle 明确包含并经过新的合同审核。

# 十六、Manifest、Checksum 和路径安全

标准适配器必须同时验证：

```text
bundle_digest
bundle-manifest raw SHA-256
Manifest artifact SHA-256
SHA256SUMS
文件实际raw SHA-256
byte_length
JSONL record_count
```

安全要求：

```text
Artifact path必须为包内POSIX相对路径
禁止绝对路径
禁止..
禁止反斜杠路径穿越
禁止符号链接逃逸受控目录
禁止重复路径
禁止大小写折叠后冲突路径
禁止未在Manifest声明的普通文件
禁止Manifest与SHA256SUMS不一致
```

Manifest声明的Artifact集合必须等于磁盘Artifact集合，加上两个保留文件：

```text
bundle-manifest.json
SHA256SUMS
```

不得静默忽略额外文件。

# 十七、事务导入流程

标准导入应分为四个阶段。

## 17.1 Validate

只读执行：

```text
Lock验证
Manifest验证
Artifact哈希验证
Schema验证
Release闭合
组件闭合
Projection闭合
Metadata闭合
Crosswalk闭合
隐私扫描
统计复算
```

此阶段不得写入数据库。

## 17.2 Stage

在单一数据库事务中写入：

```text
Bundle receipt
Artifact原始字节
Release envelope
Component references
Projection records
Canonical object envelopes
Relation envelopes
Link metadata
Crosswalk rows
Import statistics
```

所有数据保持：

```text
candidate
not active
```

## 17.3 Verify Round Trip

从数据库重建：

```text
全部公开Artifact
Release成员集合
runtime Projection
组件引用
Crosswalk
```

并与原始字节和Manifest计数比较。

## 17.4 Commit Candidate Receipt

只有 Round Trip 通过才写入：

```text
ACCEPTED_CANDIDATE
```

任何一步失败：

```text
事务整体回滚
candidate selector不变
active selector不变
Legacy selector不变
不得残留部分对象、关系或Crosswalk
```

现有 ACT 规范已经要求整包事务导入，并在哈希、组件、端点或Crosswalk任一闭合失败时不暴露任何部分数据。

# 十八、数据库持久化的最小扩展

不需要修改 Canonical 节点和关系的主体表结构。

应扩展发布收据和Artifact元数据，或在其现有JSON envelope中等价保存：

```text
bundleContractVersion
bundleId
bundleRevision
bundleDigest
bundleKind
releaseStage
manifestRawSha256
sourceCommit
sourceTag
artifactRole
artifactProfile
artifactContractVersion
artifactRequired
byteLength
recordCount
```

建议唯一性约束：

```text
(bundle_id, bundle_revision) 唯一
bundle_digest 唯一
(release_id, release_hash) 语义唯一
artifact(bundle_receipt_id, relative_path) 唯一
```

冲突规则：

```text
同一bundle_id + revision、不同digest
    → REJECT

同一release_version、不同release_hash
    → REJECT

同一release_id + release_hash、新bundle_revision
    → 允许，视为包装修订

相同bundle_digest重复导入
    → 幂等返回既有receipt
```

包装修订不得重复创建对象和关系语义行，只新增 Bundle Receipt 和原始Artifact版本。

# 十九、动态统计，不再硬编码数量

Manifest可以声明：

```text
release_entries
canonical_nodes
published_relations
各Profile节点数和关系数
rag_crosswalk_rows
component_count
relation_type_count
```

ACT必须从实际文件重新计算。

判断方式：

```text
本次Manifest声明130条关系
→ 复算必须为130

下一版本声明240条关系
→ 复算必须为240
```

不得继续把：

```text
841
744
97
1302
2个组件
```

写入长期兼容代码或 OpenSpec 的永久接口要求。

这些数字只能作为某一固定Release夹具的回归断言。

# 二十、版本差异计算

标准导入器必须根据：

```text
上一已接受ReleaseSet
→ 当前候选ReleaseSet
```

重新计算差异。

不得只信任上游 `release-diff.json`。上游Diff用于交叉验证，ACT计算结果才驱动下游失效和治理。

差异至少包括：

```yaml
objects:
  added:
  removed:
  payload_changed:
  type_changed:
  tier_changed:
  superseded:

relations:
  added:
  removed:
  predicate_changed:
  direction_changed:
  tier_changed:
  endpoint_changed:

crosswalk:
  added:
  removed:

components:
  added:
  removed:
  changed:

projections:
  added_profiles:
  removed_profiles:
  digest_changed:

vocabulary:
  added_types:
  added_predicates:
```

上游 `release-diff.json` 与 ACT 重算结果不一致时，导入失败。

# 二十一、差异后的通用治理触发

ACT 导入成功后应输出不可变的 `ReleaseSetDeltaReceipt`。

处理规则：

| 差异          | 后续处理                      |
| ----------- | ------------------------- |
| 新节点         | 进入课程覆盖和资源角色增量候选           |
| 节点标签或说明变化   | 使依赖内容摘要失效，保留Canonical身份   |
| 节点类型变化      | 高风险；原则上要求新ID或supersession |
| 节点删除        | 使覆盖、Crosswalk、资源绑定和派生结果失效 |
| 新工程关系       | 进入工程图谱，不自动成为教学关系          |
| 关系删除或改向     | 使依赖路径和图查询缓存失效             |
| 新Crosswalk  | 生成结构单元绑定候选                |
| Crosswalk删除 | 使对应ACT绑定失效                |
| 新组件         | 增量治理其新增内容                 |
| 仅Bundle包装修订 | 不重新治理语义内容                 |

同一 Canonical ID 下发生以下变化应失败关闭：

```text
entity_type改变
身份语义实质改变
原对象被另一概念替代但没有supersession记录
```

这种变化不能被当成普通内容更新。

# 二十二、兼容性自动分类

导入前生成：

```text
CompatibilityAssessment
```

## 22.1 `COMPATIBLE_CONTENT_UPDATE`

条件：

```text
Bundle合同已支持
Schema身份已支持
所有required Artifact合同已支持
仅对象、关系、组件、Crosswalk或计数变化
```

处理：

```text
普通发布接入
无需修改导入代码
无需新增Schema适配器
```

## 22.2 `COMPATIBLE_PACKAGING_REVISION`

条件：

```text
release_id/hash不变
source_dataset_hash不变
仅bundle_revision、Manifest或Artifact角色修正
```

处理：

```text
新增Bundle Receipt
不重复导入语义实体
重新验证全部公开文件
```

## 22.3 `COMPATIBLE_OPTIONAL_EXTENSION`

条件：

```text
出现未知optional Artifact
其他required合同全部兼容
```

处理：

```text
保存未知Artifact
不启用其运行语义
```

## 22.4 `ADAPTER_UPDATE_REQUIRED`

包括：

```text
未知required Artifact role
未知required Artifact contract
Projection公共结构不兼容
Crosswalk合同升级
Link Metadata合同升级
```

## 22.5 `SCHEMA_REVIEW_REQUIRED`

包括：

```text
Schema版本或哈希未知
新增规范对象类型
新增正式关系谓词
关系方向或类型签名合同变化
```

## 22.6 `INTEGRITY_REJECTED`

包括：

```text
哈希错误
组件身份缺失
端点不闭合
Manifest与文件不一致
Crosswalk越界
路径逃逸
重复身份
```

# 二十三、候选、影子和正式激活

标准包成功导入后，只生成新的候选 ReleaseSet。

流程：

```text
Bundle导入
→ Candidate Receipt
→ Repository候选Projection
→ 自动差异报告
→ 课程覆盖和资源绑定影子治理
→ Shadow验收
→ 原子移动候选指针
```

不得因兼容导入自动：

```text
切换active selector
切换RAG
切换KAQ/SAR
重建学习路径
写入Canonical学习事实
退役Legacy
```

ACT 当前正式规范也要求导入完成后继续保持 Legacy 作为生产权威。

回滚只需将候选指针恢复到上一已接受 ReleaseSet；历史 Bundle、Receipt 和治理结果均保留。

# 二十九、最终架构

```text
ActKG标准公开Bundle
        │
        ▼
ACT ReleaseSet Lock
        │
        ▼
Public Bundle Router
        │
        ├── Legacy v0.2 Exact Adapter
        │
        └── actkg-public-bundle/1 Adapter
                  │
                  ▼
       完整性与兼容性验证
                  │
                  ▼
        事务性Candidate导入
                  │
                  ▼
    AuthoritativeKnowledgeRepository
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
     图谱页面     控灵      治理影子流程
```

该设计保留现有 Repository、API、数据库知识对象和候选权威架构，只把导入边界从：

```text
固定版本适配器
```

推进为：

```text
显式Lock
+
Manifest驱动
+
Artifact角色发现
+
合同版本注册
+
增量差异治理
```

由此，后续符合 `actkg-public-bundle/1` 的模块扩展、Integration更新和聚合Release，可以通过普通发布接入和审核收据完成导入，不再为每一个图谱版本编写新的专用适配器。
