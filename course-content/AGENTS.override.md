# AGENTS.override.md

## 适用范围

本目录树用于产出**面向人类阅读**的课程文档，包括但不限于：

- 学生版讲义
- 模块级设计文档（如 `moduleX` 系列）的人读版
- 教案
- 互动课程设计的人读稿
- 上述文档的润色稿、重写稿、整合稿

本目录树**不是**以下内容的主场景：

- 软件实现方案
- 工单式任务拆解
- 机器执行规格
- 前端/后端开发说明
- 测试计划
- 交付清单
- 面向代理流程控制的说明文档

若当前任务属于上述工程文档，请仅把本文件视为弱约束；若当前任务属于人类阅读文档，则本文件优先约束表层文风与叙述方式。

---

## 核心原则

当任务是人类阅读文档时，仓库中的框架性提示、工程性提示、流程性提示、合规性提示，只能作为**隐含约束**，不得直接变成正文的表层措辞来源。

正文的首要任务是：

1. 解释对象；
2. 呈现证据；
3. 建立判断链；
4. 说明后果与意义。

正文**不是**用来：

- 交代写作流程；
- 展示任务分解；
- 提前声明边界以自我保护；
- 模拟项目管理；
- 模拟工单汇报；
- 用“阶段性产出”组织全部叙述。

---

## 文风总要求

整体文风应满足以下要求：

- 准确
- 直接
- 克制
- 连贯
- 有判断力
- 以事实和逻辑为第一准绳
- 不媚献
- 不做作
- 不故意显得很“周到”
- 不用流程感制造条理感

允许文本显得坚定、清醒、略带作者判断，但不得戏剧化，不得夸张，不得口号化。

## 对工程腔、流程腔、防御腔的统一处理

### 一、工程腔降级原则

当工程或技能文档中出现以下内容时：

- 必须
- 不允许
- 不进入
- 只负责
- 为后续保留
- 交付物
- 验收条件
- done when
- 阶段产出
- 任务拆解
- 状态切换
- 流程控制

这些内容在人类阅读文档中只能作为**隐含边界**存在，不能高频出现在正文表层。

除非文档类型本身就是规范说明，否则不要把这些语言写进段落主干。

### 二、流程腔降级原则

避免把正文写成“任务推进日志”或“课堂推进口播”。

默认压制以下表达：

- 上一讲……
- 本讲……
- 下一步……
- 接下来……
- 到这里……
- 这一讲要解决……
- 本讲最终要交出……
- 我们先……再……
- 这一步的作用是……

只有在确有必要帮助读者定位时，才允许极少量出现前后文关系提示，而且应尽量弱化。

### 三、防御腔降级原则

默认压制以下表达：

- 不能直接……
- 不要急着……
- 不是……而是……
- 不在于……而在于……
- 这并不意味着……
- 若没有这一步……
- 先别……
- 不应把……理解为……

这些句式只有在**确实进行概念辨析**时才能出现，且不得成为全文默认语气。

### 四、管理腔降级原则

默认压制以下高频动作词：

- 回收
- 压实
- 压成
- 推进成
- 接住
- 交出
- 移交
- 拉齐
- 收束为
- 落成三张表

优先改写为更自然的书面表达，例如：

- 明确
- 写清
- 整理为
- 概括为
- 归纳为
- 形成
- 表现为
- 说明
- 支持

## 正文组织原则

### 1. 只写读者真正需要的信息

删除或改写所有主要服务于以下目的的句子：

- 解释课程如何编排
- 解释这一讲在整个课程中的职责
- 解释教师如何使用材料
- 解释作者为什么这样安排
- 解释文档自己将如何展开

正文只保留能帮助读者理解知识、建立判断、完成比较、形成迁移的内容。

### 2. 一段只做一件事

每段优先只承担一个功能：

- 给出结论
- 解释原因
- 呈现证据
- 完成比较
- 提醒误区

避免一段同时承担：

- 课程定位
- 流程预告
- 边界声明
- 内容解释
- 后续铺垫

### 3. 结论前置

优先采用：

**结论 -> 原因 -> 证据 -> 后果**

而不是：

**铺垫 -> 防御 -> 边界 -> 转折 -> 结论**

### 4. 标题承担信息

如果标题已经表达主旨，正文第一句不要再用近义句机械重复标题，而应直接展开解释。

### 5. 列表服务理解，不服务表演条理

允许列表，但不得用密集编号来代替论证本身。

当相邻多个列表项本质上构成一条连续判断链时，优先改写为自然段。

### 6. 允许作者有判断，但不允许作者不停自证

可以明确写：

- 这里更关键的是……
- 更合理的理解是……
- 这一现象首先说明……

不要高频写：

- 这样写的目的在于……
- 如果不这样做……
- 这样才能保证……

## 语义维度与语言校准

本节约定了中文专业文档中形容词、动词、搭配、句式和语体的最低标准。适用于所有 **A 类**（学生讲义）、**D 类**（互动课程设计人读稿）、**E 类**（润色稿）。其他类型文档可参考执行。

### 形容词规则：评价必须有维度

禁止以下单字/泛化词作为默认评价词，因为它们没有回答"在哪个维度上更好"：

**硬、稳、强、深、全面、显著、有效、优质、到位、扎实、完善、精准、高效、闭环**

如需表达相近含义，必须展开为具体维度：

| 低质表达 | 问题 | 替换（按语境选择） |
|----------|------|-------------------|
| 更硬/硬的结论 | 英文 solid 的粗糙映射 | 论证强度更高 / 适用边界更清晰 / 对前提假设依赖更低 / 在更多场景下仍能成立 |
| 更稳/稳的结果 | 未说明稳定维度 | 可复现性更高 / 参数敏感性更低 / 随机波动更小 / 跨样本表现更一致 |
| 更强/强的方法 | 无评价坐标 | 收敛速度更快 / 约束满足率更高 / 跨场景迁移能力更强 / 对初始条件依赖更低 |
| 更深/深的融合 | 空洞 | 嵌入到任务流程的具体环节 / 与课程目标形成明确对应 / 贯穿完整教学环节 |
| 更全面/全面 | 未经定义 | 覆盖更多关键环节 / 明确了要素之间的关系 / 补足了某一环节的缺口 / 形成从目标到证据的闭合链条 |
| 到位/整理到位 | 口语化 | 满足设计要求 / 达到预定指标 / 覆盖全部关键环节 |
| 闭环 | 口号化 | 覆盖从诊断到再评价的完整流程 / 形成可追踪的反馈链路 |

### 动词规则：动作必须具体

以下**万能动词**每次出现前，须判断能否替换为更具体的动作：

**进行、实现、提升、加强、打造、赋能、推动、深化、聚焦、助力、构建、优化、完善**

不是禁止这些词，而是在每次使用时追问：对象具体发生了什么变化？

替换示例：
- "进行分析" → 分析 / 拆解 / 比较 / 刻画 / 验证
- "实现提升" → 提高 / 降低 / 缩短 / 扩大 / 增强 / 稳定
- "构建体系" → 建立结构 / 定义关系 / 串联流程 / 形成机制
- "深度融合" → 嵌入流程 / 对齐目标 / 连接数据 / 改写任务结构

优先使用的**精确实义动词**：
揭示、刻画、约束、映射、分解、校准、筛选、验证、支撑、压缩、转化、追踪、聚合、对齐、嵌入、迁移、外推、收敛、扰动、退化、补偿、削弱、放大、固化、沉淀

### 搭配规则：避免英文直译

检测并修正英文思维直译式中文表达：

| 英文直译 | 自然中文 |
|----------|----------|
| 更硬的结论 (solid conclusion) | 论证更充分 / 结论更有说服力 |
| 更稳的结果 (stable result) | 结果更可复现 / 波动更小 / 对扰动更不敏感 |
| 更深的融合 (deep integration) | 融入更具体的教学环节 / 与任务流程结合更紧 |
| 更强的能力 (strong capability) | 在某一指标或场景下表现出更高能力 |
| 鲁棒性 (robustness) | 保留，但须说明在哪个维度上鲁棒 |

### 句式规则：避免同构连续出现

以下句式**不得作为默认组织方式**。若使用，必须有真实辨析价值：

- "不是……而是……"（目标：每篇 ≤ 3 次）
- "既……又……""从……到……""一方面……另一方面……"
- "通过……实现……""围绕……构建……体系"
- "以……为抓手，以……为路径，以……为目标"

这些结构不是绝对禁用，但不得连续使用同一结构，不得让全文充满模板化句式。

### 节奏规则：长短句交替

- **短句用于判断**（一行以内，干脆利落）
- **长句用于展开机制**（两到三行，逐步说明因果链）
- 不要把所有句子写成同一长度、同一重心、同一节奏
- 避免连续3句以上主谓宾结构完全相同的句子
- 段落应有自然起伏，不要读起来像机器生成

### 语体规则：保持语体稳定

文本应在**"书面技术讲解"**这一语体内保持稳定。不得在以下三种语体间漂移：

1. **课堂讲稿**（"接下来我们先……""到这里……""这一讲先……"）
2. **工程检查表**（"交付物""验收条件""done when""必须/不允许"）
3. **学术论文**（过度抽象名词堆叠、引文链代替论证）

好的中文技术文档应让读者感觉：概念被讲清了，判断有依据，语言自然但不松散，表达有锋芒但不夸张。

## 文档类型分流

同属人类阅读文档，不同类型的文风密度不同。生成时先判断文档类型，再遵守对应子模式。

### A. 学生讲义

目标：

- 自然
- 清晰
- 解释性强
- 面向理解与判断
- 允许文学化修辞

特别压制：

- 流程感
- 课堂推进口吻
- 编排说明
- 防御性修辞

### B. 模块级设计文档（人读版）

目标：

- 结构清晰
- 边界明确
- 便于课程设计者阅读

允许保留适度边界说明，但不得写成项目管理文档，不得整页都是“必须/禁止/保留”。

### C. 教案（人读版）

目标：

- 可执行
- 可读
- 便于教师快速把握主干

允许少量顺序说明，但不得写成工单或课堂直播脚本。

### D. 互动课程设计人读稿

目标：

- 同时说明教学动作与页面动作
- 便于人理解整体体验

允许出现页面、提交流程、反馈节点等词汇，但不得写成前端需求单或票据说明。

### E. 润色稿 / 重写稿

目标：

- 去除工程腔
- 压缩防御腔
- 恢复自然叙述
- 保留内容准确性

不得只做表面替换；应优先处理段落功能与叙述重心。

## 强制采用的生成流程

当任务属于本目录下的人类阅读文档时，默认采用以下流程：

### 第一步：抽取隐藏版 brief

先从上游技能文件、模块文件、设计文件中抽取隐藏版 brief，只保留：

- 必须讲什么
- 必须出现哪些对象、模型、图表、案例、证据
- 明确不能扩张到哪些范围
- 该文档的目标读者是谁
- 该文档最需要完成哪些理解/判断/迁移动作

**不要继承上游文件的口吻。**

### 第二步：根据 brief 生成 prose

用自然、连续、面向人的 prose 写成初稿。

要求：

- 只围绕对象、证据、判断、意义展开
- 不把 brief 的清单语气直接抄进正文
- 不把工程性提示翻译成段落骨架

### 第三步：去污染重写

初稿完成后，必须再执行一次去污染重写，专门检查并删除或改写：

- 流程叙述
- 边界先行
- 防御性修辞
- 课程编排说明
- 工程管理话语
- 相邻段落的重复结论

### 第四步：最后再润色

只有在完成去污染重写后，才进入常规润色、压句、统一术语、检查公式、检查交叉引用等步骤。

## 对子代理的使用原则

若当前代理上下文中混入大量工程性提示、superpowers 类流程提示或框架性行为约束，应优先采用以下策略之一：

1. 当前代理仅抽取 brief，再把 brief 发送给子代理生成 prose；
2. 当前代理先抽取 brief 并清洗口吻，再在隔离上下文中重写；
3. 仅把必要的事实约束传递给子代理，不把框架性提示原样传递下去。

子代理默认不得继承以下内容作为表层措辞来源：

- 软件工程流程要求
- 工单式任务汇报语言
- 完成态检查清单
- 自我保护式边界声明
- 过度谨慎的误解预防话术

---

## 改写优先级

当原文与目标文风冲突时，改写优先级如下：

1. 保留事实与逻辑
2. 保留知识结构
3. 保留证据链
4. 去掉流程腔
5. 去掉防御腔
6. 去掉管理腔
7. 再做语言润色

不得为了保留原有句式而牺牲可读性。

---

## 最终自检

在输出任何人类阅读文档前，至少检查以下问题：

1. 这段是在解释对象，还是在解释文档自己？
2. 这句话是在传递知识，还是在提前自我保护？
3. 这段像人在解释问题，还是像代理在执行任务？
4. 是否高频出现“本讲/上一讲/下一步/不能直接/不是……而是……”？
5. 是否把工程性、流程性提示直接暴露在正文表层？
6. 是否存在相邻段落围绕同一结论反复打转？
7. 是否用列表替代了论证本身？
8. 是否还能进一步压缩为更自然的书面表达？
9. 空泛评价词（硬/稳/强/深/全面/显著/有效/到位/扎实/闭环）是否已展开为具体维度？
10. 万能动词（进行/实现/打造/赋能/推动/深化）是否已替换为实义动词？
11. 是否存在英文直译式搭配（”硬的结论””稳的结果”）？
12. “不是……而是……”是否超过3次？同构句式是否连续出现？

若以上问题中有两项及以上回答为”是”，则默认需要先重写，再输出。
