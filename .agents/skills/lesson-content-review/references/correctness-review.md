# 正确性审查

把课程内容审查分成四层，不要混为一谈：

## 1. 结构正确性

检查：
- 文件路径、媒体引用、manifest / sequence / card_order / node_ids 是否对齐
- 讲义、BOPPPS、卡片、媒体、runtime/review 之间是否引用一致
- 公式分隔符、标题层级、图片路径是否可消费
- 正式讲义中的图片、表格是否按出现顺序编号，并以“图1. …”“表1. …”等成品图题/表题呈现
- 正文中是否残留“图示建议”“待制作”“占位说明”“脚本验证”等作者态过程文本
- 若正文提到学生复现，是否采用“正文点名 `.m` 文件名 + 附录提供最简 MATLAB/Octave 代码”的成品形式，而不是把审查脚本或复杂控制代码直接塞进正文

## 2. 事实正确性

### 课内事实

包括：
- 定义、课内任务约束、例题题设、步骤顺序、评分规则

做法：
- 对照讲义主线、卡片、manifest、sequence 等内部源检查一致性

### 外部事实

包括：
- 任务、事迹、新闻、机构、人物、工程项目、比赛、标准、年份/日期、统计数字
- 任何具有时效性或明显依赖外部世界的陈述

做法：
- 必须联网核验
- 优先使用官方站点、标准组织、学校/机构官网、权威媒体、一手报道
- 输出审查结论时至少记录：
  - 审查对象
  - 核验日期
  - 关键来源链接
  - 结论：通过 / 不通过 / 证据不足

没有足够证据时：
- 删除该表述
- 或改写成更保守、证据边界内的说法

## 3. 科学合理性

重点不是“有没有公式”，而是“讲得通不通”：

- 定义与使用是否一致
- 条件与适用范围是否完整
- 因果链是否成立
- 量纲、方向、趋势、极限是否自洽
- 工程解释是否与所用模型相容
- 比较结论是否给出前提，而不是偷换条件

常见问题：
- 把经验结论写成绝对规律
- 把局部成立的结论写成普遍真理
- 把相关性说成因果性
- 只给结果，不说明前提

## 4. 确定性结论验证

以下内容必须优先考虑脚本复现：
- 例题数值答案
- 参数变化趋势
- 时域响应、频域响应、根轨迹、Nyquist/Bode
- 超调量、调节时间、稳态误差、裕度等指标

规则：
- 使用 `python3` + `control`
- 绘图可配 `matplotlib`
- 脚本应可复跑、可追溯
- 文字结论必须回到脚本输出核对
- 设计期验证脚本服务于审查与回写，不应被原样暴露成正式讲义正文中的“脚本验证”流程说明

## 5. 成品化表达专项检查

重点不是内容真假，而是最终面向学生的呈现是否已经脱离作者态：

- 图、表是否有正式编号与题名，而不是只放一张图链接
- 图题、表题是否真的在正文中出现，而不是只存在文件名或 alt 文本里
- 是否出现“建议画什么图”“待制作”“后续导出 runtime”“请补脚本”等制作流程语言
- 是否把审查阶段的 `python3` + `control` 验证过程直接写进讲义正文
- 若需要学生动手复现，正文是否只给简洁的 `.m` 文件名提示，附录代码是否保持最简、便于运行

发现以上问题时，不应标为“小瑕疵可忽略”，而应直接判定为需要返工的成品问题。

## 审查输出建议

写审查意见时，按以下结构组织：

1. 结构正确性
2. 事实正确性
3. 科学合理性
4. 确定性验证
5. 成品化表达

不要只写“已检查，通过”。
应明确指出：
- 哪些通过
- 哪些存疑
- 哪些必须返工
