# Tuning Rules

## 先判断是哪一类问题
- 超时偏多：先看任务是否分派过宽，再看推理强度是否过重
- 结论过重：先收紧 `developer_instructions`，再考虑降模型或降强度
- 漏判风险：先判断任务是否错用了机械执行角色，再按全局路由切换 Luna、Terra 或 Sol
- 越权扩散：优先收紧角色边界，而不是一味换模型

## 建议的调参顺序
1. 调整 `developer_instructions`
2. 调整 `model_reasoning_effort`
3. 最后再调整 `model`

## 本项目特有约束
- 课程任务必须服从 `lesson / interactive-design / interactive-lesson / lesson-content-review` 的边界
- 要求真实子代理审查的流程，不得通过收紧提示词来伪装成主代理可替代
- 获得子代理授权后，存在匹配命名角色时不得退化为自由派发；必须核对 `agent_role`、模型和推理强度
- 已决定委派的写任务使用命名写代理；主线程可以直接完成有界任务，不为隔离而机械增加交接
- 模型与推理档位遵循全局成本—能力路由，项目层不得另建冲突矩阵
- Luna 承担机械读扫、局部实现、多文件实现和回归测试；经济性不能成为扩大任务范围的理由
- Terra 承担复杂排障、长上下文、复合规划和领域语义审查；`max` 仅用于 `deep-debugger` 的复杂证据汇集或长上下文与高歧义并存
- Sol 承担高影响方向性决策、认证授权、迁移部署和独立终审；`high` 只用于仍未解决的关键风险
- 已清场审核在 diff 未变化时可沿用到提交、推送和开 PR，不得因 Git hook 重复审核
- `explorer-librarian` 默认只读，只提供材料与路径，不给最终裁决
- 当前角色继续使用经验证的 Luna/Terra/Sol 配置；不因主线程升级 Astra 自动迁移子代理。将来模型变更需核实运行时支持和代表任务效果，并同步 TOML、catalog 与校验；不得使用未经授权的 `ultra`。
